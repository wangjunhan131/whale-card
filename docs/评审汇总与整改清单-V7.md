## 一、四家的共识（按严重度）

### P0-1 评测尺子本身坏了（四家全部点名）

**他们说**：官方重跑 585/714 = 129 道题连标准答案都过不了；交集失败 95 道（抄满分答案也挂）；
「真实上限 ≈617」是减出来的估算，不是实测。**在 18% 刻度坏掉的尺子上调召回 = 在噪声里调参。**
老陆补充：95 道内战占全库 13.3%，**比真实失分（32 道 / 4.5%）大 3 倍**，而我只拆了 2 个例子就下结论。

**我方数据**：`bench/run/official_judgments.jsonl` 与 `full_judgments.jsonl` 可直接复算；95 道交集失败清单在 `bench/run/_fails_*.json`。

**改法**（GPT 的错误标签 + 老陆的拆分法合并）：
1. 95 道逐题拆成四类：`rubric 与 EXP 自相矛盾` / `同义被判缺（不加葱 vs 不要葱）` / `判分器读不懂` / `真错`。
2. 前三类按类修（改 rubric 或改判分器），修不掉的**先从评测集剔除并留档**，不许继续当"上限"。
3. 每次改召回/渲染，必须配同代码 A/B（两臂跑同一份题包）。
4. 报告口径改成：`判分地板 / 真实失分 / 失分归因` 三层，任一层缺失则结论不成立。

**验收**：95 道全部有归类；剔除后评测集与 rubric 自洽（标准答案应 100% 通过）。

### P0-2 静默失败是系统性缺陷（曦月、老陆、GPT 都提）

**他们说**：11 条 bug 里 9 条是「看着在跑其实没跑」——不是设计错，是**接线错/没接/没发现**。
`/health` 只能看进程活着，看不到「原文表三天没涨」。**静默失败比崩溃严重，因为崩溃有人修。**

**改法**（曦月给的清单，我加严格化）：给每条链路加**日结对账**，写进 `/health` 明细，红了才叫健康：
- `dialogue` 今日新增 > 0（或有新 /remember 却为 0 → 红）
- `habits` / `impression` 非空且 `last_ts` 在今天
- 桥工具数 = 18；`qq_guard` 进程数 = 1
- 语义索引条数 = 可见卡条数；`mem_archive` 增长率
- `/context` p95 延迟（>10s 报警）、`/report` p95 延迟
- 最近一次成功写入时间、最近一次备份时间、timeline head 与卡是否同源
- 后台维护线程心跳（上次 fade / 上次挖矿 的时间）

**验收**：人为制造一次「原文表不涨」（临时改错 source）→ `/health` 必须在 5 分钟内变红。

### P0-3 45 天长期召回，病在**排序**不在窗口（四家共识，但修法分歧）

**他们说**：老陆最看重我那条诊断——「ret20 召不回的 47 道里 **0 条已被删**：11 道时间窗误筛、1 道 self 预筛、30 道在候选里但排 20 名外、5 道噪声」。
曦月据此建议 `top_k 20→50`、`_cap 5-12 → 10-20`；GPT 建议多阶段流水线 + 二阶段 rerank + 召回 trace。

**我方数据 `[我方数据]`**：P01 的 ret20 已经 **92.0%**（88 题），真正缺的是**其他 persona 的 45 天档**
（P12 58%、P16 53%、P20 65% @ hit@5）。加宽 5→12 在 714 题上只拿到 **+1.4pp**（窄问句 0 变化）。
→ **结论：加宽不是方向盘；top_k 20→50 也先别盲从，要先按 persona 测 ret20。**

**改法（按顺序）**：
1. 先给 P12/P16/P20 补 ret10/ret20 数据（`adapt_retrieval.py --cfg ladder` 已支持），拿到真实分布。
2. 若「排 20 名外」占比仍大 → 改**排序特征**：加「实体命中 / 事件时间匹配 / 记忆类型 / 询问意图」四项加权（GPT 的混合排序特征），而不是单纯放大候选集。
3. 加**召回 trace**（GPT 的核心建议）：记录原始 query / 归一化 query / 候选数 / 每道过滤原因 / 各分项得分 / 最终 top-k / 实际注入的 mem id。这是唯一能让「为什么没召回」变成可复算的手段。
4. 多事实问题查子问题拆分（「分别说说」「当时有哪些」）——现在的 `_is_multi_fact()` 只放大配额，没做分题检索。

**验收**：0/3/15/45/90 天分桶报 Recall@5/10/20 + MRR；**45 天 Recall@10 ≥ 85%**；短期档不回退。

### P0-4 事件时间 ≠ 写入时间（GPT 独有，但成立）

**他们说**：`create_ts` 是"系统何收到"，不是"事情何时发生"。事后补述、延迟同步、跨平台导入、回填数据都会错。
例：11-01 发生、11-05 才讲；问「11-01 发生了什么」按 create_ts 筛会漏。

**我方现状 `[已核]`**：`query_time_span()` 精确到天时卡的是 `create_ts`（有注释说明"不看 last_active_ts"）。
回填的 761 条 dialogue 就是典型的"事件时间≠写入时间"。

**改法**：记忆增 `event_time` / `event_time_precision`（unknown/approximate/range/date）/ `timezone`；
写入时若能从文本解析出相对日期（`normalize_time` 已有）就落 event_time，否则 `create_ts` 兜底并标 `recorded_only`；
检索优先 event_time，缺失时退化 create_ts 且在上下文里写明「记录于 X，事件时间未知」。

**验收**：构造「事后补述 / 只说月份 / 上周三 / 日期范围」四类样本，能区分并表达不确定性。

### P0-5 唯一性只在"带卡出门"那一刻验证（曦月）+ 需要协议化（GPT）

**他们说**：锚 2503/卡 2503、链分叉就拒绝同步——这套只在 `disks/sync` 生效。
运行时没有"另一个我"的检测：两个进程同时写、同一库被两份桥接挂、旧会话还在跑。
GPT 要 `identity_id / instance_id / device_id / run_id / writer_epoch / timeline_head` 分开，
配 `writer_lease`（主权令牌）+ epoch 递增，旧设备持过期 epoch 只能只读；克隆必须显式选「迁移」或「分支」。
锚要含版本/ID/head/schema/签名；锚损坏进恢复流程，不许自动重建。

**改法**：先做**运行期单写者租约**（`writer_lease` 表：instance_id + epoch + 心跳 ts）；
启动时抢租约，抢不到就进**只读模式**（`/report`、`/remember` 返回 409 并说明「另一个我在写」）；
`/health` 暴露 epoch 与租约持有者。之后再补 identity.branch/migrate 的显式命令。

**验收**：同时起两个实例打同一个卡 → 第二个必须只读或拒绝写，不许两边都写。

### P0-6 中期池没有出口，是"有倒计时的炸弹"（老陆、GPT、我方诊断一致）

**他们说**（老陆）：库里 984 条从没被召回；进门线之后无 TTL；按衰减曲线约 150 天成批删除；
冷档只保证"不丢"，不保证"想得起来"；**这不是"还没做完"，该单独标日历提醒**。

**我方数据 `[已核]`**：`LAM_M = 2.70e-7 /秒`（**半衰期 29.7 天**，不是老陆猜的 1.98 秒）。
进门线 `THETA_MEDIUM = 0.35`，侵蚀线 ~0.02。从 w0=0.67 起：**27.8 天跌破 0.35**（无动作）、**150.5 天到侵蚀线**。
11-09 重分池把 `t_anchor` 全设成当天 → 炸弹从"写入日"重算，预计 **2027-04-08 前后**成批。
另：`mem_archive` 已经保证"不删内容"，但"想不起来"仍是真的。

**改法**：三层出口
1. **降级而非删除**：中期池到期前 30 天自动降 long（不再走侵蚀线）；
2. **复述仪式**：对高频被召回但没晋升的，用一次"重述"生成新卡并重置 TTL（老陆的建议）；
3. **成批结算保护**：单次维护最多清 N 条（如 20），且清理前写 `pending_archive` 预览表，可回滚。

**验收**：模拟 12 个月 → 无任何单次批量丢失 > 20 条；中期池规模稳定而非单向膨胀。

## 二、P1（该做，但不挡发布）

### P1-1 self 话语统一 +0.32 是"修了一个实例，不是模式"（老陆 + GPT）
- 老陆追问：为什么 self/user 会走两条分支、一条加了系数一条没加？四类 region（fact/preference/self/habit）里还有没有同类漏加？
- GPT 要求：按类型分权重（身份/长期目标/承诺/已验证经历/一般对话/临时猜测/角色扮演/已纠正），
  命题保留状态（未完成/完成/取消），猜测保留不确定标签；**区分"记住我说过 X"与"相信 X 是事实"**。
- 改法：`remember(region=...)` 按 region 给不同 bonus；上下文渲染加前缀（"他曾这样说" vs "已核实"）。
- 验收：同时看**存活率**与**事实误用率**（只有存活率会鼓励乱记）。

### P1-2 动机由"空闲时间"驱动 ≠ 心理（GPT）
- 拆 trait / state / goal / drive；空闲时间只能是**弱特征**；floor 要么移除、要么注明只用于数值稳定；
- 每次变化记 `trigger_event / old / new / reason / formula_version`；
- 反事实测试：同样空闲 6 小时、不同交互历史，状态不应相同。
- 我方现状：`motiv_tick` 已接线、想念改目标式、`bump` 有 0.15 地板（为防"一点都不想他"）。→ 需补 trigger 账本与反事实测试。

### P1-3 内脏 24 变量缺数据字典（GPT + 老陆追问）
- 老陆追问最狠：**24 个量里有几个进了 `/context` 的【内脏】格？** 若只进 3-5 个，其余 19 个是"给人看的仪表盘"。
- 改法：每个变量写 名称/语义/范围/单位/更新周期/公式/输入事件/下游用途；无用途的合并或移出生产上下文。
- 我方现状 `[已核]`：viscera 有 24 个量 + 每 120 秒静息采样；`/context` 的【内脏】格只取少数几个做主述。→ 需列清单。

### P1-4 印象/习惯要分场景与功能（GPT）
- 习惯记 `scene / 表达功能 / 频次 / 最近出现 / 置信度 / 适用范围`；严格分离 user impression 与 self habit；
- 区分表达习惯 / 行为习惯 / 稳定偏好（证据标准不同）；弱提示 / 强提示 / 禁用三档。
- 我方现状：已做行为类合并（12 类）+ `full>=2` 整句短话闸 + 场景桶，但**没记"表达功能"**，也没分三档强度。

### P1-5 梦层要五阶段 + 幂等（GPT）
- ingest / summarize / link / validate / commit；`idempotency_key` 防重复提交；摘要留 dialogue_id + 原文区间 + 模型版本；
- 冲突进待确认队列；积压/失败重试/死信。
- 我方现状：`/dream/commit` 已有 `dialogue_ids`，但没有幂等键（宿主超时重试会重复写入）。

### P1-6 冷档要三种删除语义（GPT）
- `forget`（降召回/归档）/ `suppress`（禁止普通与冷档召回）/ `purge`（真正清除，含向量索引、缓存、备份、外部端）；
- 删审计事件但不留原文。
- 我方现状：只有 archive，没有 suppress/purge。

### P1-7 工程复杂度上升 + 单接口压力太大（**GPT 两条，用户点名要改**）

**(a) 核心模块职责过重**
- GPT 原文（问题 12）：`card2.py` 362KB 单文件同时管 记忆仓储 / 生命周期 / 检索 / 上下文装配 / 时间线 / 身份；
  改一处会牵动多处（文档里披露的锁互等事故就是证据）。
- 建议：先**同进程内模块化**（不为微服务而拆进程）：`MemoryRepository` / `LifecycleService` / `RetrievalService` / `ContextAssembler` / `TimelineLedger` / `IdentityManager`，
  每个模块定义 输入输出 schema、事务边界、错误类型、锁规则、幂等要求。

**(b) 单个接口压力太大**
- 现状：`mind_server.py` 一个进程、一把 `mind.lock`、`/context` 一次要跑 语义+覆盖+时间窗+分舱+预算装配；
  `/report` 一次写 mem + detail + dialogue + synapse + timeline + impression + habits。
  实测过 `/context` 70 秒假死、`/report` 28876ms —— 所有入口挤在一条全局锁上。
- GPT 建议：全局锁依赖图、禁止持核心锁调可能反取锁的函数、**写操作集中到单写队列**、
  后台任务分批+超时+可取消+心跳+重试上限、接口要 `request_id` / 结构化日志 / 错误码、
  禁止 `except: pass` 吞关键写入（**我方 `[已核]`：card2.py 里 `except Exception:` 共 134 处**）、
  加 WAL checkpoint / 锁等待 / 事务时长 / 队列积压指标。

**改法（分三步，每步可独立验收）**
1. **读路径去锁**：`/context` 装配改用只读连接 + 短事务，不持全局 `mind.lock`（现在它拿锁是为了 `tick`，把 tick 挪到独立维护线程 + 独立锁）。
2. **写路径串行化**：单写线程 + 有界队列（`queue.Queue(maxsize=256)`），`/report` `/remember` 只入队不直写，返回 `request_id`；
   队列深度写进 `/health`；写失败进死信（`dead_letter` 表），不吞。
3. **模块拆分（只拆边界，不搬代码）**：先把 `card2.py` 里 6 个职责的**入口函数**标出来，加一层 `services/` 门面（薄封装，内部仍调 card2），
   再逐个把实现搬过去。这样每一步都能跑现有测试，不会一次性重写。

**验收**：`/context` p95 < 3s、`/report` p95 < 1s（不回退功能）；队列积压 / 锁等待 / WAL 尺寸进 `/health`；
`except: pass` 在写路径上清零。
