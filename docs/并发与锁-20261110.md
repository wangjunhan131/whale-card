# 并发与锁 · 现状与规矩（V7 第 6 件）

写于 2026-11-10。这份不是设计愿望，是**现在代码里真实的样子** ——
每一条都对应一次实际踩过的坑，或者一次明确的「为什么这里不拿锁」。

## 一、有几把锁

| 锁 | 在哪 | 保护什么 |
|---|---|---|
| `mind.lock`（RLock） | `mind_server.Mind.lock` | 一张卡的所有读写：`/context`、`/report`、`/remember`、`/tick` 全都先拿它 |
| 写者租约（文件锁 + TTL） | `disks.py` 的 `acquire_lease/heartbeat_lease` | **跨进程**：同一张卡同时只许一个进程写，其他进程降级只读 |
| SQLite 自己的写锁 | 数据库 | 事务级；跟上面两把是不同的层，**混着用最容易互等** |

`card2.MemoryCard` **自己不加锁**。它连接属性叫 `self.db`，串行化全靠外层的 `mind.lock`。
所以任何直接 `import card2` 去写卡的脚本（工具、探针），都在锁之外 —— 只能对副本动手。

## 二、拿锁顺序（唯一的合法顺序）

```
请求线程：  mind.lock  →  SQLite 写事务
维护线程：              SQLite 写事务（不拿 mind.lock）
```

**反序 = 死锁。** 2026-11-09 现场：

```
维护线程：持 mind.lock → 调 impression.fade() → 自己开连接写 impression → 等 SQLite 写锁
请求线程：持 SQLite 写事务 → 等 mind.lock
```

表现不是「报错」，是：端口在听、进程活着、`/health` 和 `/context` 全部超时、
18 个连接挂在 CloseWait、`/report` 用了 28.8 秒。**看起来像网络问题，实际是锁反了。**

修法（已落地）：维护线程写自己的表时**一个锁都不拿**；确实需要和请求互斥的那件事
（习惯挖掘，它要开两个连接）改成 `mind.lock.acquire(blocking=False)` ——
拿不到就跳过这一跳，晚一小时挖掘没人察觉，卡住一秒所有人都察觉。

## 三、规矩（写新代码时照着抄）

1. **持 `mind.lock` 的时候，不许打开新的数据库连接。**
   要写别的表，用当前已开的连接；要开新连接，先出锁。
2. **维护线程/后台线程默认不拿 `mind.lock`。** 非拿不可时用非阻塞 `acquire`，
   拿不到就跳过，绝不排队等。
3. **不要在持锁时调用可能回头找锁的函数**（典型：`impression.fade`、`habits.mine_and_write`、
   `checkpoint.write` —— 它们自己开连接）。
4. **写入口一律走 `/report` 的单写队列**（`mind_server` 的 `wq_*`）：队列上限 256，
   超时返 202，避免并发写把 SQLite 忙等拖成一分钟级别。
5. **只读进程不许写**：抢不到租约 → `readonly=True` → 写接口 409 `readonly_lease_held`，
   跳过快照/出生证/锚写入。只读进程退出时**不许** release 别人的租约（已修）。
6. **卡外的脚本（bridge / console / 快照工具）直连 card.db 时一律只读**
   （`file:...?mode=ro`），它们不受 `mind.lock` 管，写进去就是绕过所有规矩。

## 四、吞异常：不许静默，允许降级

铁律：**关键写路径上的失败必须留痕。** 旁路功能（语音、头像、可视化）失败可以只降级，
但要能看出来。

已经真吃过的亏：

- `add_dialogue` 的 `NOT NULL constraint failed: dialogue.source` 被 `except: pass`
  吞了**两周** —— 原文表再没长过一条，谁都没发现。现在至少打一行 stderr。
- 维护线程的锁反转被吞成「超时」，查了两轮才定位。

现在的机制：

- `card2.soft_fail(kind, e)`：计数 +1，**同一种错只往 stderr 打第一行**（避免刷屏埋掉线索），
  其余只记数；`kind` 短而稳定。
- `card2.soft_fail_snapshot()` → 出现在 `/health` 的 `reconcile.checks.soft_fail`，
  24 小时内有计数就亮黄灯 `soft_fail:<kind>`。
- 已接的三处：`dream_w0`（梦记忆起点权重）、`remember_dedupe`（判重失败）、
  `worklog_dedupe`（工作日志判重失败）。

现状盘点（`probe/_audit_swallow.py`，2026-11-10）：

- 关键写路径 `card2.py` 还有大量 `except Exception: pass`，但绝大多数在
  「读预算、读配置、格式化输出」这类不影响数据完整性的分支上；
- **这次只改了写路径上的三处**，没有全量清零 —— 清零的代价是把「降级」也变成「报错」，
  那会让一个可选功能失败直接毁掉一次对话。

## 五、怎么发现「锁又不听话了」

1. `/health` 的 `reconcile.checks.latency.groups.context.p95` 超过 5 秒（样本 ≥5）亮黄灯。
2. `/report` 单次超过 5 秒 → 写队列返 202（202 就是「排不进去了」，不是成功）。
3. 症状对照：端口在听 + `/health` 超时 + 连接挂 CloseWait = **几乎一定是锁反了**，
   不是网络、不是模型慢。
4. 排查顺序：先看维护线程最近有没有改过「拿锁 + 开新连接」的组合，再看写队列积压。
