## 关键结论

1. 单流 `/context` 其实只有 ~1.8 s；评审里的 6.9 s 是**并发下被锁串行化放大**的结果。
2. 锁内最大的单笔是 `flow_time()` 里的 `card.tick(dt)`：**每个请求都把世界推进约 1 秒的心跳/情绪/激素结算**，占锁内时间 55%。
   这正是评审说的「把写活塞在读路径锁里」——心跳本该由维护线程按固定节拍做，不该由「谁来问一句话」驱动。
3. `assemble`（touch=True 会写）与 `recall` 都是几百毫秒级，属于正常量级，不是主矛盾。
4. 冷启动第一个请求 45 s（`assemble` p95 44 s）是加载/预热，不是稳态问题，但要单独记录，别混进中位数。

## 下一步（按计划第 2 步之前先做的一个小改动）

## 顺手做掉的第二步：把 tick 挪出读路径（2026-11-11 14:34）

`card.tick(dt)` 不该由「谁来问一句话」驱动。新增 `_start_world_tick(mind)`
守护线程（`mind_server.py`，线程名 `world-tick`，默认 60 秒一拍，
`WHALE_WORLD_TICK_SEC` 可调 / 置 0 关闭），在锁内结算
`card.tick(dt)` + `log_hormones` + `touch_alive`；请求路径只在
「后台 4 分钟没结算过」（`WHALE_TICK_SEC`，默认 240）时兜一次底。

实测（同一台机、串行、20 次）：

| 指标 | 挪之前 | 挪之后 |
|---|---|---|
| `/context` total p50 | 1807 ms | **685 ms** |
| `/context` total p95 | 7726 ms | 1767 ms |
| 锁内 hold p50 | 1755 ms | **672 ms** |
| `flow_time` 段 p50 | 918–960 ms | **0.1 ms** |
| `assemble` / `recall` p50 | 338–476 / 278–296 ms | 312 / 297 ms |

`/perf` 新增 `world_tick: {last, err, beat_s}`：没人在说话时也看得见世界在走
（实测 14:36:50 那一拍正常，`viscera_hist` 同步推进）。

剩下的慢点就只剩 `assemble`（~310 ms）和 `recall`（~300 ms）这两笔读，
以及并发时的等锁——那才是第 2 步「`/context` 走只读连接、不拿全局锁」要解决的。

## 第 2 步：`/context` 读阶段不抱全局锁（2026-11-11 下午）

**做了什么**
- `card2.py`：主连接改名 `_db_main`，`db` 变成 property（读线程取 `_DB_TLS.conn`）；`_thread_conn()` 每线程一条独立连接（`busy_timeout=30000`）；新增 `@contextmanager reading()`，退出时把残留事务 rollback 掉（否则读连接留个长读事务，WAL 没法 checkpoint，压测时 `-wal` 涨到 12MB+）。
- 读阶段只读不算账：`assemble_context(..., access=False)`、`recall(..., access=False)`；「被想起」那笔记账（召回事件 / 会话命中 / 突触加固 / 内脏刺激）攒进 `_defer_q`，回短锁里 `apply_recall_effects()` + `flush_deferred_effects()` 一次写完。
- 舱（pods）重建丢后台：`_ensure_pods()` 有旧舱就起后台线程重建（30 秒节流，`_POD_BUILD_LOCK` 单飞），只有冷启动才同步建 —— 舱只是粗筛，旧的照样能用。
- `mind_server.py`：`_ctx_unlock()` 开关（`WHALE_CTX_UNLOCK`，默认 0 = 旧行为）；`/stacks` 诊断端点（只读，列全部线程栈）。

**数字**（副本 8899，3 读×4 + 5 写×3）

| --- | --- | --- | --- |
| 改造前（锁内） | 2187 ms | 2327 ms | 1282 ms |
| 只去锁（读里还夹着写） | 1056 ms | 23183 ms | 0 |
| ＋记账延后 | 1199 ms | 17860 ms | 0 |
| ＋舱重建丢后台 | 1150–1190 ms | 12000–34000 ms | 0 |
| 串行单请求（生产） | 690–740 ms | — | — |

**诚实的结论**：去锁把「排队」吃掉了（`lock_wait` 掉到 0，p50 腰斩），但压测的 p95 还有十几秒尾巴。抓栈看清楚了——**不是数据库**：卡在 `_build_pods()` 的纯 Python 双重 `cos_sim`、`skill.all()` 之后的逐条评分，再加上查询向量编码 207 ms/次，12 路并发一起抢 GIL。数据库那条线（WAL + busy_timeout + 线程连接）已经干净了。

所以第 3 步（连接管理）之后还得补 CPU 侧：查询向量缓存、`cos_sim` 换 numpy 批量、舱的语义质心预算好。

**验证**：生产重启后 `tools/smoke.py` 20/20、`/context` 七格齐、串行 ~0.7 s；`WHALE_CTX_UNLOCK` 仍默认关——尾巴没消掉之前不切默认。

## 第 3 步：CPU 侧——「每请求重复算的」改成「一次算好」（2026-11-11 下午）

第 2 步把排队问题解决掉之后，`/perf` 的尾巴全落在 `assemble` 里，抓栈也不是 SQLite。于是照 `probe/_prof_ctx.py` 的剖面逐项砍：

- **IDF 行向量缓存**（`card2.MemoryCard._idf_sim`）：原来每条候选都现算 na、nb 两个循环（实测每请求 1315 次 `cos_sim_idf`、156 ms），可 query 侧固定、行向量也固定。现在行向量乘完 idf 的形态和模长按 `(id, idf 身份, 向量对象身份)` 缓存，查询侧只乘一次。数值等价性自测 300 组、0 不一致。
- **连接池**（`_conn_acquire/_conn_release`，上限 8）：原来按线程缓存，可 HTTP 是「一个请求一个线程」，等于每请求新建 SQLite 连接（54 ms/请求，而且线程一死连接就漏）。现在借出/归还，跨线程复用。
- **BLAS 线程夹到 2**（`mind_server.py` 最顶上设 `OMP/OPENBLAS/MKL/NUMEXPR/VECLIB`）：numpy 默认按核数开线程，12 路并发时 12×N 个线程互抢核 —— 实测 `assemble` 段从 300 ms 飙到 66 s，这一条是尾巴的真凶。
- **启动清理延后 45 秒**：印象碎片清理原来在启动瞬间就抢 `mind.lock`（要扫全库），把重启后的头一分钟堵死（实测 `/context` 等锁 46 秒）。改成延迟线程做，结果一样。
- **世界推进的 dt 夹到 300 秒**：重启后的空档别一次性灌进 `card.tick`。

**数字**

| 阶段 | 单请求 | 12 路并发热压（warm） |
| --- | --- | --- |
| 改造前 | 840 ms | p50 2187 ms / p95 23–34 s |
| ＋IDF 行向量缓存 | 610 ms | — |
| ＋连接池 | ~600 ms | p50 1325 ms / p95 7.4 s |
| ＋BLAS 线程夹 2 | — | **p50 774 ms / p95 1.0–1.3 s**（墙钟 3.5 s） |
| 生产串行（8848） | 542–807 ms | — |

**要诚实说明**：每次进程重启后的**第一波**仍然慢（冷启动建舱、词表、连接，~10–20 s），上表是稳态数字。下一步如果还要压冷启动，把舱（pods）落盘缓存是最直接的一刀。

## 第 4 刀：冷启动（2026-11-11 下午）

重启后的第一句话原来要等十几秒。查下来是两件事：启动时清理线程抢锁（已改成延迟 45 秒），以及舱（pod）聚类在冷启动时同步跑。

| 场景 | 首请求 | 第二、三次 |
|---|---|---|
| 改造前（同步建舱） | 48697ms（生产，清理线程还抢着锁） | 2.1s / 1.1s |
| 冷启动改后台建、无缓存 | 11841ms | 1019ms |
| 冷启动 + `cache/pods.json` 读回 | **2210ms** | 574 / 582ms |
| 生产（有缓存，含模型预热） | 4992ms | 535–655ms |

做法：`_ensure_pods()` 冷分支先 `_pods_load()`，读不到就起后台线程建（不再同步等），建完 `_pods_save()` 写 `card/cache/pods.json`（纯缓存，删了只是下次重建慢一点；key = 带向量条数 / N_PODS / 迭代数 / 语义维度，对不上就当没有）。

两个坑记下来：
1. `card2.py` **没有 import io**，`_pods_save()` 里写 `io.open` 直接 NameError，又被 `except Exception` 吞掉 —— 表现成「缓存永远不落盘」。改用内建 `open`。
2. `_pod_sem` 是 `{舱号: numpy 数组}`，JSON 存再读回来变成 list，`_pod_candidates` 里一算 `'list' object has no attribute 'shape'` 就 500。读回时要 `np.array(v, dtype=np.float32)`。

已知限制：并发写压测下偶发 `database is locked`（`remember_dedupe` / 写队列），500 会返回给压测客户端。生产是单用户低频写入，未观察到。

## 第 3 步：连接管理正式化 + 读阶段去锁默认打开（2026-11-11 傍晚）

**连接管理**

- `journal_mode` 是库属性，启动时设一次（WAL；可移动盘/网络盘退回 DELETE），现在会**读回来记下真正生效的值**（`self._journal_actual`），`/perf` 的 `db.journal_mode` 直接能看到 `wal`。
- 新增 `_tune_conn(conn)`：`busy_timeout=30000`、`synchronous=NORMAL`、`temp_store=MEMORY`、`cache_size=-16000`。之前读池新建的连接**只设了 busy_timeout**，`synchronous` 是每条连接自己的、默认 FULL —— 写的时候白多一次 fsync。
- 读池上限走 `WHALE_READ_POOL`（默认 8），`/perf` 的 `db` 段给 `journal_mode / pool / pool_max / opened`。

**去锁开关默认改成 1**（`WHALE_CTX_UNLOCK=0` 可回滚）

|---|---|---|
| 去锁关 | 1574ms | 1672ms |
| 去锁开 | **804ms** | **1064ms** |

## 顺手修掉的两个「一重启就出事」（2026-11-11 傍晚）

**一、杀进程重启之后，服务变只读，而且再也起不来可写的**

现象：`/health` 里 `readonly=true, readonly_reason=lease_held`，租约 holder 指向一个已经死掉的 pid，`lease_state` 明明报 `expired`，可新进程就是不接手。两次部署都卡在这，只能手工 `DELETE FROM writer_lease` 再重启。

根因：`disks.acquire_lease()` 只看「租约有没有过期（TTL 90 秒）」，不看「持有者那个 pid 还在不在」。kill -9 之后 90 秒内重启，新进程看到一份「还没过期」的租约，就乖乖进只读；而且它不重试，于是永远只读。

修法：同主机 + 持有者 pid 已经不存在 = 它不会再写任何一个字节，直接接手（`not (_same_host and _pid_alive(...))` 才拒绝）。改完实测：kill 后插件立刻拉起，`readonly=False`，smoke 20/20。

**二、压测副本把真卡的锚写脏了（`anchor_tampered`）**

现象：`/health` 的 `reconcile.checks.anchor = anchor_tampered`，`anchor.json` 里的 `db` 字段变成了 `%TEMP%\whale-load\card_load.db`、条数是副本的 3451 —— 真卡 1340 条记忆、链头 3081。

根因：`anchor.write()` 里「状态是从哪张卡读的」和「锚写到哪个文件」是两条独立推断，极端路径下能对不上；`_conn_path()` 问不出连接路径时会退回默认卡 `DB_PATH`。

修法：写之前加硬护栏 —— `state["db"]` 和锚标签不是一个文件就**拒绝落盘**（宁可这轮不写锚，也不写错证据）。然后用真卡重建了一份锚（`anchor.write(conn, force=True)`，`db` 正确、条数 3081），直接跑 `anchor.check()` 判 `ok`。

教训：跑副本压测时，实例的 `--db` 是临时库，但 `anchor.json` / `checkpoints` 这类「卡外证据」默认还是落在项目目录，得显式用 `WHALE_ANCHOR_LOCAL` / `WHALE_ANCHOR` 指走。另外 `/health` 里的 `reconcile` 是**上一轮维护的快照**，不是实时值，改完别急着看它。

## 第 5 步：稳定性（2026-11-11 傍晚，用户口径「预热别再压了，保证稳定和启动可靠」）

改性能到这一步已经不是瓶颈问题，剩下的是「半夜会不会自己坏掉、坏了能不能自己爬回来」。这一段全部只做加法，没有改任何业务口径。

### 1. 启动自检（`_start_boot_check`，thread `boot-check`，延迟 6 秒）
服务起来 6 秒后自己回答一遍「到底能不能用」，结论挂 `mind._boot`，`/health` 顶层与 `reconcile.checks` 都能看到：

| 检查 | 含义 |
|---|---|
| `mem_rows` | 库能读、记忆条数对得上 |
| `journal_mode` | 必须是 `wal`（否则并发读会被写堵） |
| `db_writable` | 建表→写入→删除跑一遍（真写，不是猜） |
| `pods` | `{ready, cache_kb}`：舱是否已在内存、落盘缓存多大 |
| `promise_table` | 承诺账本表在不在 |
| `world_tick` | 后台世界推进线程在不在 |
| `readonly` | 有没有被租约判成只读 |

`tools/smoke.py` 新增两项读它的结论：「启动自检」「库是 WAL」——现在 smoke 是 **22 项**。

### 2. WAL 阈值 checkpoint
WAL 不 checkpoint 只会长（实测长到 26MB）。维护线程每跳看一次：间隔 ≥ `WHALE_WAL_CKPT_SEC`（默认 1800 秒）且 WAL ≥ `WHALE_WAL_CKPT_MB`（默认 64MB）就 `PRAGMA wal_checkpoint(TRUNCATE)`。
副本演练（`WHALE_WAL_CKPT_SEC=5`、`WHALE_WAL_CKPT_MB=0`）：日志出现 `[mind] WAL checkpoint：0.0 MB → 已截断`，WAL 归零 —— 说明这条链是通的，生产上按 64MB 阈值等着就行。

### 3. 舱缓存坏了能自己爬回来
`_pods_load` 读坏文件时：改名 `cache/pods.json.bad-<时间戳>` 留证 → stderr 打一行 → 返回 False → 下一轮后台重建。

### 7. 后台线程活着没在动（2026-11-11 傍晚）
最隐蔽的坏法不是崩，是「服务还在回话，但世界不再往前走」：世界推进线程死了 → 情绪/激素不再结算；写队列死了 → 记忆不落地；维护线程死了 → 印象不淡、习惯不挖。这三种都不会让 `/health` 变红。

补法：
- `/health.threads` = `{world_tick, write_queue, maint, boot_check}`；前三者报 `true/false`，`boot_check` 报 `done/running/null`（它是一次性任务，跑完线程自然结束，不能算「死了」）。
- `/health.write_queue` = `{done, failed, rejected, last_ms, last_rid, depth, maxsize}` —— 队列堵没堵、上一笔花了多久，一眼可见。
- `_reconcile` 里加红线：三个线程任一 `is_alive()==False` → `red: <name>_dead`；`None`（功能被显式关掉）不算坏。
- `tools/smoke.py` 加第 23 项「后台线程都在」。

实测：`threads={"world_tick":true,"write_queue":true,"maint":true,"boot_check":"done"}`，`write_queue={"done":0,"failed":0,"rejected":0,"depth":0,"maxsize":256}`，smoke **23 项 FAIL 0 WARN 0**。

### 8. 恢复演练：备份能不能真的站起来（2026-11-11 傍晚）

### 9. 写冲突：短退避重试（2026-11-11 傍晚）
压测里偶发过 `database is locked`：`remember_dedupe` 静默退回、写队列任务失败一次就没了。SQLite 报 locked 不是故障，是「此刻别人在写」。

- `mind_server.Mind.wq_run(fn)`：在**写队列线程**里跑任务，撞到 `locked`/`busy` 就短退避重试（50/100/200ms + 抖动，`WHALE_WQ_TRIES` 默认 4 次），其它 OperationalError 原样抛。
- 只重试锁冲突：`no such table` 这类错误重试也没用，立刻抛。
- `/health.write_queue.locked_retry` 记累计重试次数 —— 它能看出「最近是不是一直在跟别人抢写锁」。
- 自测：构造一个前两次抛 locked、第三次成功的函数 → 结果 `ok-3`、`locked_retry=2`；换成 `no such table` → 立即抛出、不重试。
- 为什么不在请求线程里重试：等的这几百毫秒会占住一个 HTTP 线程，正是评审里「不许把延迟摊到请求上」那条。
