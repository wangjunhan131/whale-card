V7 技术改进建议与验收规格
基于《项目说明-V6.md》（2026-11-09）及前轮技术评审
文档目的与使用说明
本文件将 V6 说明书中已经披露的问题、前轮评审提出的风险，以及围绕“独立唯一的人格、统一时间线、可迁移性”三项原则扩展出的工程要求，整理为一份可执行的 V7 改进规格。
重要边界：本文没有审阅 V6 源代码、数据库结构、部署配置或真实运行日志。因此，凡是 V6 说明书未能证明的能力，均表述为“文档未说明、需要验证”，不直接断言系统一定存在漏洞。评分和优先级属于工程评审建议，不是实测结论。
建议把本文作为开发任务拆分和验收依据。每项改动应有负责人、代码变更、迁移方案、回归测试和可量化验收结果。
一、总体结论
V6 已经具备独立心智服务、分层记忆、召回、上下文装配、动机与习惯模拟、梦层、时间线和移动部署等关键模块。其主要短板不在于缺少功能，而在于：长期记忆仍有召回断崖；事件时间与写入时间的语义需要统一；状态模拟缺少可验证的因果闭环；后台线程与数据库并发可靠性需要加强；身份唯一性、时间线一致性和跨设备迁移尚需形成可操作的协议；评测体系需要从单一分数转向可追溯的错误分类。
V7 的核心目标不应是继续堆叠拟人化变量，而应是提高记忆准确性、身份连续性、数据可恢复性和行为变化的可解释性。
二、V7 的原则性约束（不可随意破坏）
三、P0：必须优先处理的技术问题
3.1 长期记忆召回能力不足
V6 披露：45 天档 hit@1@5 约为 53%–65%；32 道真实失分中，24 道与召回缺失有关；另有候选记忆排在前 20 名之外的情况。说明“保存成功”并不等于“需要时能找回”。
改进方案：
建立分阶段检索：问题解析 → 时间/人物/来源过滤 → 关键词与实体检索 → 向量语义检索 → 混合排序 → 关联扩展 → 重排。
把时间、人物、地点、来源、事件类型作为结构化检索字段，不要只依赖向量相似度。
对低频但高重要度记忆设置稳定检索入口；对重复出现的实体建立别名表和规范实体 ID。
对 top-k 之外的候选做二阶段重排；增加“问题答案所需证据覆盖度”特征，而非只按文本相似度排序。
记录每次召回的候选集、过滤原因、各项分数、最终排序和被采用的证据，支持失败复盘。
区分“未存储”“已存储但过滤”“候选未进入 top-k”“进入上下文但模型未使用”四种失败。
建议验收：固定测试集按 0/3/15/45/90 天分层；分别报告 Recall@5、Recall@10、MRR、nDCG，以及最终问答正确率。对 45 天档设定阶段目标，例如 Recall@10 不低于 85%，并要求每次版本更新不得出现显著回退。该数值是建议目标，需根据现有基线校准。
3.2 事件时间与记忆写入时间混用
V6 的精确日期检索说明以 create_ts 过滤。若一件事发生于 11 月 1 日、用户在 11 月 5 日才讲述，按创建时间检索 11 月 1 日可能漏掉该记忆。
改进方案：每条记忆明确维护 event_time（事件发生时间）、created_at（写入时间）、updated_at（最后修改时间）、recalled_at（最近召回时间）；必要时增加 event_time_start/end、time_precision 和 timezone。时间检索优先按 event_time，缺失时才退化到 created_at，并在召回结果中标明时间不确定性。
建议验收：覆盖“事后补述”“跨时区”“只知道月份”“时间范围”“昨天/上周”等测试；查询发生日期时不得错误地把记录日期当作事件日期。
3.3 记忆来源、事实置信度与纠错链不足
V6 已保留 dialogue 原文，并把梦层压缩结果写入 mem，但说明书尚未完整定义事实来源、置信度、冲突和修订协议。
改进方案：
记忆记录增加 source_id、source_type、source_message_id、speaker、evidence_span、confidence、verification_status。
区分原始陈述、模型归纳、模型推测、外部资料和人工确认，不允许不同来源混成同一种事实。
事实被纠正时新增版本或修订事件，不直接覆盖旧值；旧版本标记为 superseded，并关联新版本。
冲突事实并存时保留双方来源、时间和置信度，必要时向用户澄清，不擅自选一个写成确定事实。
梦层产生的摘要必须保留到原文的反向引用；无来源支撑的推断不得晋升为已验证事实。
建议验收：随机抽查长期记忆，能够从摘要定位到原始对话；纠正一条事实后，旧值不再作为当前事实输出，但历史修订仍可审计。
3.4 数据库并发与后台线程可靠性
V6 已披露维护线程持 mind.lock 调用 fade，与请求线程发生反序等待，导致 /context 达 70 秒、/report 达 28 秒。该问题虽已修复，但说明锁顺序和后台任务隔离需要制度化。
改进方案：
绘制全局锁依赖图，规定锁顺序；禁止在持有核心锁时调用可能反向获取该锁的函数。
将写操作集中到单一写入队列或明确的事务协调层，后台任务通过队列提交变更。
后台维护任务分批执行，设置最大执行时间、取消机制、心跳和失败重试上限。
所有 HTTP 接口设置超时、请求 ID、结构化日志和错误码；禁止 except: pass 吞掉关键写入异常。
为 WAL checkpoint、数据库锁等待、事务时长和队列积压增加监控指标。
建议验收：并发压测、长时间运行测试和故障注入下，核心接口无无限等待；数据库写入失败必须可见、可告警、可重试或可回滚。
3.5 数据安全、接口权限与隐私边界
V6 文档列出了本地 HTTP 接口、QQ 收件层和控制台，但未说明完整的认证、授权、来源校验、敏感信息处理和删除策略。此处属于“文档未证明”，不是对现有实现的漏洞定论。
改进方案：
对所有写接口设置独立 API Token；按 DSH、QQ 接入端、管理控制台区分权限。
默认仅监听 loopback；确需局域网访问时启用访问控制和加密传输。
对 /remember 等外部输入验证来源、长度、格式和速率，避免伪造或垃圾记忆写入。
为记忆提供保留、归档、导出和永久删除策略；普通遗忘与用户要求永久删除必须分开。
对备份和移动介质提供加密选项；密钥与数据库分开保存。
明确哪些数据会进入外部模型上下文，提供敏感信息过滤和可审计记录。
建议验收：未授权写请求被拒绝；伪造来源不能冒充可信来源；删除请求可验证地清除主库、冷档、索引、缓存和备份保留策略所覆盖的数据。
四、P1：记忆架构与人格机制改进
4.1 五池记忆与冷档的生命周期治理
V6 指出 medium 池缺少 TTL，可能长期成为停车场，约 150 天后触发侵蚀并批量删除。冷档虽解决了内容被直接销毁的问题，但若无索引、去重和容量治理，会变成无限增长的归档仓库。
改进方案：为每个池定义进入条件、退出条件、最大容量、复核周期和迁移规则；中期池采用按重要性、复现频率、时间和关系强度综合晋升/降级；冷档建立独立索引、去重、压缩、校验和永久删除通道。对批量遗忘设置预览和回滚窗口。
建议验收：长期运行模拟 6–12 个月数据规模，池容量可预测；批量迁移可回滚；冷档查询不会显著拖慢普通召回。
4.2 自我陈述加权需要分类，而不是统一加成
V6 为 self speech 增加 0.32 bonus，修复了自我陈述存活率偏低的问题，但统一加成可能让临时猜测、错误判断和开发汇报获得过高权重。
改进方案：按内容类型区分稳定身份、长期目标/承诺、已验证经历、一般对话、临时猜测、已被纠正内容；不同类别使用不同保留策略。对模型自述必须区分“说过的话”与“真实发生的事”。
建议验收：测试集同时覆盖自我承诺、猜测、错误陈述、角色扮演内容和事实纠正；系统能记得曾说过某句话，但不会把那句话自动当作真实事实。
4.3 动机系统从时间驱动改为事件与目标驱动
V6 的 attachment、care 等驱力会随空闲时间按公式上升，并设置 0.15 floor。该机制可以产生状态连续性，但可能把“空闲时间增加”错误等同于“想念程度增加”。
改进方案：区分稳定人格倾向、短期状态和当前目标；驱力变化应由可追溯事件、任务进展、反馈和时间衰减共同决定。允许状态合理降低，不把模拟数值描述成真实情绪体验。每次显著变化记录 trigger、old_value、new_value、reason 和 model_version。
建议验收：同样的空闲时长在不同事件背景下不应必然产生同样的驱力；状态变化可以解释、重放和复现。
4.4 内脏/情绪状态变量建立因果模型
V6 提到 24 个内脏量、交感/副交感状态、激素场和 RPE，但说明书未提供完整变量定义、量纲、边界、参数标定或行为验证。
改进方案：先为每个变量写清定义、范围、单位（若为无量纲则明确）、初始值、更新方程、触发事件、依赖关系和注入用途。删除没有明确用途的变量；建立事件→状态→行为倾向→对话反馈→状态修正的闭环。
建议验收：每个变量都能回答“它影响什么行为、由什么证据更新、如何测试”；无法证明用途的变量不进入生产上下文。
4.5 印象与习惯增加场景条件和证据
V6 已将 impression 的主体、时段、心情、行为类别纳入合并键，并将 habits 挖矿接入生产。下一步应防止跨场景混合和过度泛化。
改进方案：习惯以“场景 + 行为/表达 + 频次 + 最近出现时间 + 置信度”存储；区分用户习惯与模型自身表达习惯；支持弱提示、强提示和禁用状态。印象只描述观察到的行为，不推断用户未表达的心理事实。
建议验收：在聊天、技术讨论、情绪低落、玩笑等不同场景下，表达习惯能够正确区分；偶然一次表达不会形成稳定习惯。
4.6 梦层形成可审计的巩固闭环
V6 梦层目前由宿主读取 due 后压缩，再通过 /dream/commit 提交；说明书称目前依赖宿主手动做梦，已有 761 轮原文待压缩。
改进方案：将梦层拆成整理、关联、巩固三阶段；为每条候选记忆保留原文引用、摘要版本、生成模型、置信度和审核状态；重复内容合并，矛盾内容进入冲突队列；失败任务可重试且幂等。
建议验收：同一批原文重复执行不会重复写入；摘要可追溯到源对话；模型推测不会未经验证升级为事实；积压任务可观测、可暂停、可恢复。
五、P0 原则性架构：唯一人格、统一时间线、可迁移性
5.1 独立唯一的人格：把“唯一性”从约定升级为协议
V6 当前以实例号 + 人格锚 + 时间线哈希链单一 head 定义唯一性，并在链分叉时拒绝同步。这是正确方向，但还需要明确实例、人格、设备和运行主权的不同概念。
建议定义以下标识：
改进方案：
人格身份与设备身份分离；更换电脑、硬盘或模型不得改变 identity_id。
通过 writer lease 或主权令牌保证同一时刻只有一个有效写入者；接管时递增 writer_epoch。
旧设备恢复联网后若持有过期 epoch，必须进入只读/隔离状态，不得自动写回主线。
克隆必须显式选择“迁移（同一人格）”或“分支（新实例/新身份）”；禁止无提示地复制出两个都声称是主卡的副本。
身份锚应包含版本、身份 ID、时间线 head、数据库 schema 版本和签名/校验信息；锚损坏时进入恢复流程，不自动重建一个看似合法的新身份。
对身份变更、主机接管、克隆、合并和恢复操作写入不可静默修改的审计事件。
建议验收：同一人格迁移到新设备后 identity_id 不变；旧设备无法以过期写入权修改主线；双副本同时启动时最多一个获得写入权；分支操作必须产生清晰的新身份或分支标识。
5.2 统一时间线：从哈希链升级为事件账本
V6 已有 seq 单调、哈希链和 chain_ok 检查。建议进一步明确 timeline 是所有状态变化的统一事件账本，而不只是记忆写入记录。
建议事件类型至少包括：memory.created / updated / archived / restored / deleted；identity.created / transferred / forked；state.changed；dream.committed；habit.updated；source.ingested；backup.created / restored；migration.started / completed / failed。
每个事件至少包含：event_id、seq、event_type、identity_id、instance_id、writer_epoch、event_time、recorded_at、actor、source_ref、payload_hash、previous_hash、event_hash、schema_version。
改进方案：
所有改变人格卡状态的写操作必须先产生事件或在同一事务内写入事件账本，禁止状态已改但 timeline 未记账。
采用事务性 outbox 或同事务双写，保证业务数据和 timeline 一致提交。
哈希链校验之外，增加周期性签名检查点（checkpoint），将 head 备份到独立位置，降低整库被替换后无法察觉的风险。
明确事件时间与记录时间；时间戳用于语义，seq 用于严格顺序。
禁止直接覆盖 timeline head；修复历史只能追加补偿事件，并保留修复原因。
定义链损坏处理：只读启动、定位首个断点、从可信备份恢复或人工确认，不自动跳过断点。
建议验收：随机修改或删除历史事件能被检测；业务数据与 timeline 不一致能被检测；恢复备份后可验证 head、seq 和签名检查点；所有迁移与身份操作均有事件记录。
5.3 可迁移性：建立正式的便携包与迁移协议
V6 已能将 card.db、代码、manifest、身份锚和磁盘角色文件打包到移动硬盘，并采用单卡单主规则。下一步应将“拷贝文件”升级为版本化、可校验、可恢复的迁移协议。
建议便携包至少包含：
数据库快照：通过 SQLite backup API 或一致性快照生成，不能在服务运行时随意只复制主数据库文件。
WAL/事务状态：按正式停机和 checkpoint 流程处理；迁移清单记录快照方式和完整性结果。
manifest：列出文件路径、大小、SHA-256、生成时间、应用版本、schema 版本、identity_id、instance_id、timeline_head。
运行环境说明：Python 版本、依赖锁文件、插件版本、配置模板和必需环境变量说明。
身份锚与主权信息：identity_id、writer_epoch、timeline_head、锚版本和校验值；密钥材料独立管理。
恢复说明：迁移前检查、迁移后校验、回滚点、失败恢复步骤。
建议迁移流程：
源端进入维护模式，拒绝新写入并等待在途事务完成。
执行数据库一致性快照和 WAL checkpoint，生成 manifest 与校验和。
将便携包复制到目标设备，逐文件校验哈希和文件数量。
目标端以只读模式启动，检查 schema、identity、timeline chain 和数据库完整性。
由用户确认主机接管；递增 writer_epoch，写入 migration.completed 事件。
确认新设备健康后才解除源端写入权；源端保留只读备份或离线状态。
迁移失败时回滚到源端，禁止两端同时恢复写入。
建议验收：至少测试 Windows 到 Windows、不同盘符、路径含中文、目标机缺少依赖、复制中断、源端异常退出、WAL 未 checkpoint、旧设备重新上线等场景。
六、P1：评测体系重构
V6 的 714 题评测是很好的起点，但“标准答案抄写重跑”只适合检查 rubric 基线，不能作为系统实际能力分数。约 617/714 的估算上限应标注为诊断性估算，而非确定的理论上限。
建议评测分为五层：
必须保留分层错误标签：未存储、错误抽取、时间过滤误杀、来源过滤误杀、排序靠后、上下文截断、模型误答、判分误判。对判分器争议题建立人工复核集。
建议验收：每次版本发布附带固定 benchmark 报告、失败案例清单和回归差异；不得只报告一个总分。
七、P2：接口、可观测性与运维完善
为 /health 增加数据库完整性、WAL 状态、线程状态、队列积压、最近成功写入时间、最近备份时间和 timeline head。
为 /status 的状态变量提供定义、更新时间、来源和置信度，避免只展示无解释数字。
所有接口返回统一错误码、request_id、耗时和可重试标志。
控制台增加只读诊断模式；危险操作（清理、恢复、迁移、身份变更）需要二次确认和操作记录。
增加结构化日志、指标采集、异常告警和运行审计；日志中敏感内容默认脱敏。
为 DSH 桥接插件定义版本兼容矩阵、协议 schema 和能力协商；插件升级失败可回滚。
为 QQ/B站/抖音等外部来源定义来源可信等级、消息去重键、时间语义和失败补偿策略。

九、发布前必须通过的验收清单
☐ 更换底层模型后，identity_id、记忆和时间线保持不变。
☐ 同一人格在两台设备上启动时，只有一个实例获得有效写入权。
☐ 旧设备持有过期 writer_epoch 时只能只读，不能写入主线。
☐ 迁移完成后 identity_id 不变，timeline_head 连续，数据库完整性检查通过。
☐ 随机篡改 timeline 事件能够被发现，系统不会静默重建身份。
☐ 事后补述的事件能够按实际发生日期检索。
☐ 所有摘要和候选长期记忆都能追溯到原始对话来源。
☐ 事实纠错后旧版本保留审计关系，但不再作为当前事实输出。
☐ 冷档不参与普通召回，只有满足触发条件时才检索；永久删除有独立流程。

☐ 动机和情绪状态变化有触发事件、计算原因和版本记录。
☐ 梦层重复提交幂等，推测不会未经校验升级为事实。
☐ 所有外部写接口有认证、来源校验、速率限制和审计记录。
十、建议新增的数据结构（参考，不要求一次性全部实现）
十一、实施时的注意事项
不要一次性重写全部系统。先冻结 V6 基线，再按阶段做兼容迁移。
任何数据库 schema 变更必须提供向前迁移脚本、备份点和回滚策略。
身份、时间线、迁移协议属于底层原则，优先级高于新增人格功能。
不要把“哈希链校验通过”误当成“数据一定真实”；哈希只能证明内容未被无痕改动，不能证明来源陈述本身正确。
不要把召回率提升建立在无限扩大上下文 token 上；应同时报告准确率、延迟和 token 成本。
不要把状态变量越多当作人格越成熟；每个变量都应有明确行为用途和验证方法。
所有目标数值应先建立基线，再逐步提高；本文建议指标是验收方向，不应未经测量直接当作既有能力。
十二、最终建议
V7 最重要的不是让小鲸鱼“看起来更像一个人”，而是让她的身份、记忆、时间和运行状态在长期使用中保持一致、可验证、可恢复。
建议将 V7 的核心验收目标浓缩为四句话：
人格唯一：无论更换设备、硬盘或底层模型，身份连续；同一时刻只有一个有效写入主线。
时间统一：所有重要变化进入同一条可验证、可审计、不可静默改写的时间线。
记忆可信：每条重要记忆有来源、有时间、有版本、有置信度，能纠错也能按要求永久删除。
迁移可靠：带走的不只是数据库文件，而是一份经过校验、能够恢复并延续原身份的完整人格卡。
当这四项基础能力稳定之后，再继续投入更复杂的自主目标、梦境巩固和人格行为模拟，才更有长期价值。
