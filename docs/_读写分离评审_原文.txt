读写分离专项
技术评审与改造建议
围绕 SQLite WAL、应用层锁、连接管理与异步写入
评审建议稿 1.0｜2026 年 11 月
一、结论先行
本次问题的核心不是 SQLite WAL 缺乏并发读写能力，而是应用层用同一把 mind.lock 把读写人为串行化；同时，写路径把 embedding、consolidate、原文落库、时间线写入和统计记账等耗时操作放在锁内，显著拉长了锁持有时间。
已提供的压测现象：5 组写请求（每组 3 次）与 3 组读请求（每组 4 次）同时访问 8848；/context 中位耗时 6881ms、p95 7602ms、最慢 8680ms；/report 单条耗时 1.25–2.4s。这些数字作为本次讨论提供的基线，改造前后应使用同一脚本、数据规模和机器环境复测。
推荐路线：以方案三为目标架构；方案一与方案四作为第一阶段低风险改造；方案二作为连接管理基础设施。方案三必须补齐事务边界、任务可靠性和一致性设计，不能仅仅把耗时函数扔进内存后台线程。
核心决策：读请求不参与写锁竞争；核心写入只做短事务；耗时计算在事务外；后台任务可恢复、可重试、可幂等；所有派生结果可追溯到源事件和处理版本。
二、现状问题与根因判断
2.1 当前链路的问题
这条链路把数据库事务、应用层互斥锁和计算型/整理型任务混在一起。embedding 与 consolidate 通常不是必须在主写事务内完成的操作；trace 和 soft_fail 记账也不应无条件延长核心记忆写入的临界区。
2.2 为什么读请求也会排队
如果 /context 在读取前也获取 mind.lock，那么即使 SQLite 处于 WAL 模式，读请求仍会先被应用层互斥锁挡住。
WAL 的并发优势只有在应用层允许读连接独立读取、且读事务足够短时才能体现。
单连接复用会限制并发；但单连接不是唯一根因。若所有请求都被 mind.lock 串行化，单纯增加连接数也无法根治。
请求级新建连接并重复执行 WAL 等 PRAGMA，可能带来额外初始化开销与锁竞争；是否确实发生，需要连接创建日志和 PRAGMA 频率验证。

三、四个方案逐项评估
3.1 方案一：只读连接，读请求不获取 mind.lock
评价：适合最先落地，改动较小，能直接消除读请求在应用层等待写锁的问题。
建议：/context、/report 等纯查询路径使用独立只读连接（例如 SQLite URI 的 mode=ro），读请求不获取 mind.lock；读连接设置合理 busy_timeout，查询使用短事务。
关于 stale 标记：不建议把“可能读到旧数据”一律标成 stale。响应应携带 snapshot_revision 或 snapshot_at；只有当读取版本落后于调用方要求的最低版本，或超过业务允许的延迟阈值时，才标记 stale。
优点：降低读写互斥；改造简单；不需要先引入复杂连接池。
局限：不能解决写请求之间的 SQLite 单写者竞争，也不能解决写路径内部持锁过长。
注意：只读连接仍受 SQLite 快照与锁规则约束；长读事务可能阻碍 WAL checkpoint 回收旧页面。
读事务结束后再做序列化、模板拼装、模型调用、网络请求和渲染。
3.2 方案二：固定连接池（读连接 + 写连接）
评价：是合理的连接管理方式，但不是本次问题的第一根因修复。应建立在读写路径已分离、事务边界清晰的基础上。
建议起点：一个专用写连接，2–3 个只读连接；最终数量由压测决定。SQLite WAL 是多读者加单写者模型，不是多写者并行模型，写连接池不宜盲目扩大。
启动时统一初始化连接配置；避免每个请求创建连接并重复设置 journal_mode=WAL。
每条连接明确线程归属，或采用已验证的线程安全连接管理策略；不要未经确认跨线程共享连接对象。
每条新连接配置必要的 busy_timeout、foreign_keys 等连接级参数；journal_mode=WAL 应在数据库初始化/迁移阶段设置并验证。
连接池应具备借出/归还、超时、关闭、异常连接剔除和指标统计。
连接池改善连接复用与读并发，但不能让 SQLite 同时执行多个写事务。
3.3 方案三：写路径切分为“快写 + 慢活”
评价：长期收益最大，是目标架构核心。但必须从“后台线程”升级为“可恢复的后台任务机制”。
最重要的设计点：后台任务记录必须与核心数据在同一个 SQLite 事务中提交。否则可能出现“核心记忆已写入，但任务入队失败”，或“任务已入队，但核心记忆回滚”。推荐采用 Outbox 模式：核心写入和任务记录同事务提交，Worker 异步消费。
3.3.1 三层锁规矩
数据库事务：只保护必要 SQL 读写；事务内禁止 embedding、模型调用、网络 I/O、文件 I/O 和长时间计算。
应用层写入协调锁：只协调同一进程内的写操作顺序；纯读请求不得获取。持锁区只做短小、可预测的操作。
后台任务领取/状态：通过任务表的原子状态迁移实现，不用全局 mind.lock 包住任务执行全过程。
“锁内只做 INSERT/UPDATE、持锁 50ms 以内”是合理的工程目标，但不能在未测量前当成保证值。应以 p50、p95、p99 持锁时长验收，并在不同数据规模下测试。
3.3.2 后台任务必须具备的可靠性
持久化队列：任务记录落数据库，进程重启后仍可恢复，不依赖内存 queue。
幂等：每个任务有唯一 task_id / idempotency_key；重复消费不得重复生成或污染结果。
状态机：pending → running → succeeded；失败可进入 retry_wait，超限进入 dead_letter。
租约与回收：running 任务记录 lease_until / heartbeat；Worker 崩溃后，过期任务可重新领取。
退避重试：指数退避并加入随机抖动，避免故障恢复时任务同时重试。
任务版本：记录 processor_version，避免旧任务用新规则静默覆盖新结果。
积压监控：监控 pending 数量、最老任务年龄、失败率、重试次数和 Worker 吞吐。
优先级与限流：防止后台任务把 CPU、磁盘 I/O 和 SQLite 写入通道占满。
必须区分主数据与派生数据：原始记忆和身份时间线中的关键事实属于主数据；embedding、索引、摘要、统计等通常属于可重建派生数据。如果时间线事件是不可丢失的业务事实，应在主事务中持久化基础事件，不能当作可丢弃的后台统计。
3.4 方案四：读路径批量短事务
评价：应与方案一同时实施。它能避免 WAL 长读事务，降低锁等待并稳定响应时间。
将 /context 数据访问整理为一次或少量固定查询，在短事务内批量读取记忆、索引、状态和版本信息。
事务结束后，再在内存中排序、拼装、裁剪和渲染。
避免循环中逐条打开连接或执行大量小查询（N+1 查询）。
不要在持有读事务时等待模型、磁盘文件、远程服务或用户输入。
为上下文设定最大条数、最大字节数、最大查询时间；超限按优先级裁剪并记录原因。
若多条查询必须看到同一快照，应放在同一个短只读事务中；不要跨多个事务拼出不一致结果。
四、推荐目标架构
架构原则：读请求不参与写锁竞争；核心写入只做短事务；耗时计算在事务外；异步任务必须可恢复；派生结果可追溯到源事件和处理版本。
五、SQLite 与锁管理规范
5.1 WAL 与连接初始化
journal_mode=WAL 属于数据库级模式配置，宜在启动初始化阶段执行并检查返回值；busy_timeout、foreign_keys 等连接级设置应对每条新连接配置一次。synchronous=NORMAL 是性能与持久性权衡选项，是否采用取决于项目的数据安全要求，不能只为压测数据降低持久性保障。
5.2 事务规范
事务必须短小，避免事务内执行不可预测耗时操作。
避免在一个事务里同时完成原始数据写入、embedding、模型调用和全文整理。
事务失败明确回滚；重试区分 SQLITE_BUSY、约束冲突、磁盘错误等类型。
设置合理 busy_timeout，并结构化记录超时，不要无限等待。
监控 WAL checkpoint；关注 WAL 文件持续增长、长读事务和 checkpoint busy。
5.3 mind.lock 职责重定义
不建议继续把 mind.lock 设计成“所有访问 Mind 数据的总锁”。应缩小为应用层写入协调机制，或在数据库事务方案明确后逐步移除。
六、数据一致性与异步化风险控制
6.1 定义一致性等级
建议核心记忆主记录在提交后立即可读；embedding 和 consolidate 可异步完成。/context 应能识别“主记录已存在但派生处理尚未完成”，不能把尚未生成 embedding 的记忆误判为不存在。
6.2 revision 机制
为每次核心写入分配单调递增 revision（或全局事件序号）。API 响应携带 event_id、revision 和 processing_state；读接口返回 snapshot_revision。由此判断读取是否包含指定写入，而不是仅凭时间猜测 stale。
七、建议的数据表与后台任务设计
以下仅为结构示意，不要求原样照搬。实施前先核对现有 schema，避免重复建设或破坏兼容。
任务领取应在短事务中完成：选择符合条件的任务并原子更新为 running，同时设置 lease_until。若 SQLite 版本支持 RETURNING，可评估 UPDATE ... RETURNING；否则可使用 BEGIN IMMEDIATE + 条件更新，并检查受影响行数。Worker 领取成功后立即提交事务，再在事务外执行任务。
任务执行结束后，用短事务写入派生结果并更新任务状态。更新时校验任务仍由当前 lease/token 持有，避免租约过期后旧 Worker 覆盖新 Worker 的结果。
八、分阶段实施路线
不建议一次性重写全部读写层。每个阶段单独上线、单独压测，出现回归时可以快速定位引入问题的层次。
九、压测与验收标准
当前已知基线：/context 中位 6881ms、p95 7602ms、最慢 8680ms；/report 单条 1.25–2.4s。目标应在相同硬件、数据库规模、请求分布和并发组合下测量。
9.1 必测场景
纯读压测：多个 /context 与 /report 并发，确认读请求不获取 mind.lock。
读写混合压测：复现 5×3 写 + 3×4 读，并增加更高并发阶梯。
写入突发：观察写事务时长、队列积压和 API 返回时间。
Worker 关闭：写入期间停止 Worker，确认主数据提交且任务保留。
Worker 崩溃：任务执行中强制终止，确认租约过期后可重新领取。
重复消费：重复投递同一 task_id，确认幂等。
数据库繁忙：制造 SQLITE_BUSY，确认超时、重试和错误返回。
长读事务：观察 WAL 增长和 checkpoint 状态。
磁盘空间不足/写入失败：验证主事务回滚，不产生半完成状态。
备份恢复：确认 WAL 模式下备份、恢复和一致性校验流程正确。
十、监控与日志
每个请求携带 request_id，每个核心事件携带 event_id，每个后台任务携带 task_id。性能排查优先记录元数据，不要把完整私人记忆原文或敏感上下文写入日志。
十一、常见错误做法与禁止项
不要让 /context、/report 等纯读请求继续获取全局 mind.lock。
不要把 embedding、模型调用、consolidate、网络请求或文件操作放在数据库事务内。
不要在每个请求中反复执行 PRAGMA journal_mode=WAL。
不要把内存 queue 当作唯一任务队列；进程重启不能导致任务消失。
不要假设后台线程天然安全；线程安全、连接归属、异常处理和退出清理必须明确。
不要为了读到最新数据而让读事务长期不提交。
不要盲目增加 SQLite 写连接数量；SQLite 仍然是单写者模型。
不要将关键时间线事实当作可丢弃统计；先区分主数据与派生数据。
不要只用平均响应时间验收；必须观察 p95/p99 和尾延迟。
不要在未做备份、恢复和故障注入测试前直接替换生产数据库访问层。
十二、最终执行清单
先补可观测性：拆出 mind.lock 等待时间、持锁时间、SQL 事务时间、embedding/consolidate 时间。
立即改造纯读路径：只读连接、不拿 mind.lock、批量取数、短事务后内存拼装。
统一连接初始化：启动时设置 WAL；建立固定读连接管理和单写连接；避免请求级反复创建连接和设置 WAL。
改造写路径：核心事件与 Outbox 任务同事务提交；embedding/consolidate 等在事务外执行。
后台 Worker 使用持久化任务表、幂等键、租约、重试、死信和积压监控。
为 API 加 revision 与 processing_state，明确强一致和最终一致边界。
每阶段按同一压测脚本验收，并执行崩溃、重复消费、checkpoint、备份恢复测试。
