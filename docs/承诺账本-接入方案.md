## 1. 接入点

### 1.1 读侧：往上下文塞一段（**必做**，约 6 行）

**位置：`card2.py:6838`** —— `sections["dream"] = len(_dm)` 那行之后、`state = self._state_line()`（`card2.py:6839`）之前。

```python
        # ⑤.95 【没结清的事】—— 只影响语气，不改事实格
        try:
            from promises import due_promises as _due_p, promise_block as _p_blk
            _now = time.time()
            _due_p(now=_now)                      # 幂等 sweep：open→due
            _pb = _p_blk(now=_now, limit=3)
            if _pb:
                out.append(_pb)
                sections["promise"] = len(_pb)
        except Exception:
            pass
```

为什么放这儿：

- 紧跟 ⑤.8 worklog / ⑤.9 做梦 之后，同属「每轮可能变、只影响语气」的尾块。**不打断 ②③④ 的缓存前缀**（那几格才是 context caching 的大头）。
- 不动 `_fact_pos`（`card2.py:6411`）后面的【事实】格；承诺不是事实，不能进事实块 —— 总文档的铁律就是「事实块与行为块必须分开拼」。
- `out.append` 在 `"\n\n".join(out)`（`card2.py:6844`）之前，末尾追加不影响任何已有格的下标。

### 1.2 写入侧：三处（**MVP 只需 1.3 的最小版**）

1. **抽取**：用户说「明天一起把卷子弄完」→ `add_promise(what, due_ts, who="user")`。最小规则版复用 `cardtime.normalize_time()` 把「明天」锚成日期、当天 12:00 不够精确，**承诺需要时分**，建议：有 `HH:MM` 用它，没有就用 20:00（他的作息里「晚上」的默认落点），再不行 `due_ts=0`（无期限，永不进 due）。
2. **兑现**：用户说「弄完了/交了/睡了」→ `close_promise(pid, "kept")`。候选匹配**只认最近 1 条 due 的**，多条则跳过（照抄 `match_completion` 的 `ambiguous` 处理，宁可漏判）。
3. **取消**：用户说「算了/不弄了」→ `close_promise(pid, "cancelled")`。

MVP 可以只做「读侧注入 + 手工/脚本写入」，先验证「到期项出现在上下文里、语气会变」，再上抽取。抽取走 LLM 工具调用比规则稳，但那是下一轮的事。

### 1.3 结算侧：失约 → RPE（**第二步再做**）

位置建议放在「每轮开头、拼上下文之前」——也就是 `assemble_context` 一进来（`card2.py:6245` 附近）或 `mind_server` 处理消息前：

```python
for row in promises.due_promises(now, grace_hours=12):     # 超 12h 宽限判失约
    settle_plan_outcome(kind_of(row), row)                  # → Appraisal → engine.step
```

`settle_plan_outcome` 照 `probe/_promise_proto.py` 的 `settle()` 写，**三个要点**（都已在原型里验证）：

1. 预期写进 `eng.expect[ap.scenario]`，别写 `plan:kind:topic`（vendor 的键对不上，见适配备忘 §7.1）。
2. 封顶要**循环**缩放，单次不收敛（见 §7.2）。
3. 冷却键 `f"{kind}:{what}:{outcome}:{pid}"`，12h 内不重复结算 —— 否则每轮扫一次，同一笔账每轮扣一次，情绪会塌。

## 2. 对 `context` 预算的影响

- 预算：`ctxweight.BUDGET_DEFAULT = 6000`（`ctxweight.py:43`），`effective_budget()` 由 runtime_config 覆盖。
- 实测（原型输出）：1 条 → **66 字**（含块头 7 字 + 1 行 34 字 + 禁令行 25 字）。
- 满 3 条：约 **130–160 字**；`promise_block(max_chars=220)` 是硬上限，再多也截断。
- 占比：以字数口径 **1.1%（1 条）～ 3.7%（满 3 条 + 上限）**；token 口径同量级（中文 1 字≈1 token）。
- 三个边界情况都是 **0 字**：没有到期项 / `WHALE_PROMISE=0` / 表不存在（`OperationalError` 被吞）。**无承诺时上下文与现在逐字节相同。**

## 3. 回滚

| 层级 | 做法 | 效果 |
|---|---|---|
| 软回滚（推荐） | `WHALE_PROMISE=0` | `promise_block()` 直接返回 `""`；上下文恢复原样；写路径仍可用（便于事后排查「当时到底记了什么」） |
| 停写 | 不调 `add_promise` | 表里的旧账留着，但没人写新的 |
| 硬回滚 | `DROP TABLE IF EXISTS promise;` + 删 `promises.py` / 两处 import | 无残留；`timeline` 链不受影响（承诺表不在链上，**这是刻意的**） |

`WHALE_PROMISE` 默认未设 = 开。与现有开关风格一致（`WHALE_RECALL_TRACE=0`、`WHALE_EXPECT_RESET`、`WHALE_GATE`）。

另：`WHALE_PROMISE_DB` 可把账本指到另一张卡（原型就是用这个指向 `%TEMP%` 副本）。生产不设，走默认 `card.db`。

## 4. 验收清单

### 4.1 必过（对应本轮要求）

- [ ] **到期承诺进上下文**：造一条 `due_ts = now-15h` 的账 → `assemble_context()` 的 `text` 里出现 `【没结清的事】`，且 `sections["promise"] > 0`
- [ ] **未到期的承诺不进**：`due_ts = now+20h` 的账不出现在 `text` 里
- [ ] **失约后那次结算 RPE 为负**：`settle()` 返回 `rpe < 0`，且 `DA` 下降、`CORT` 上升（原型实测 −0.256 / DA −0.256 / CORT +0.302）
- [ ] **无承诺时零开销**：`promise_block()` 返回 `""`，`assemble_context()` 输出与关闭开关时逐字节相同（空库 / 空表两种情况都要测）
- [ ] **`WHALE_PROMISE=0` 时整块消失**：同一份数据，开关前后 `text` 只差承诺那一段

### 4.2 接入前必须补测

- [ ] **幂等**：连续调 `due_promises(now)` 10 次，`state` 只在第一次 `open→due`，不重复改
- [ ] **宽限**：`grace_hours=12` 时 `due` 在 12h 内不判 `broken`；超了才判，且 `closed_ts` 只写一次
- [ ] **表不存在不炸**：删掉 `promise` 表后调 `promise_block()`，返回 `""` 而不是抛栈（上下文拼装路径不能有未捕获异常）
- [ ] **冷却**：同一笔账 12h 内结算两次 → 第二次 `applied=False`，调质无变化
- [ ] **上下文抖动**：开关前后跑 20 轮固定对话，`est_tokens` 差值 ≤ 40
- [ ] **不污染召回**：`promise` 表不进 `mem`、不进 `recall_trace`，向量召回结果与开关无关

### 4.3 上线后观察（一周）

- [ ] 到期项是否**被念出来**（她复述「你说好要…」）—— 若出现，加强块内禁令或干脆去掉 `what` 原话只留「有件没结清的事」
- [ ] 深夜（23:00 后）是否出现催账 —— 建议 `promise_block` 加时段判断：23:00–07:00 只注入「有一件没结清的事」，不列明细
- [ ] 失约结算是否过于频繁（每天 > 2 次）—— 说明 `grace_hours` 太短或抽取太宽

## 5. 明确不做的

- 不改 `timeline.py` 的链：承诺表**刻意不在哈希链上**。链是「发生过的事」的不可篡改证据；承诺会改状态（open→due→kept），混进链要么破坏不可篡改语义，要么每改一次就留一条假「事件」。
- 不进 `mem` 池：不进召回、不参与衰减 —— 承诺的「变淡」由 `expected_now()` 的半衰期管，不该让记忆衰减曲线再叠一层。
- 不搬 `topic_alias` 同义词表、`events` 18 字段、`post_check` 三个出戏检测（理由见适配备忘 §6.2）。

| 改在哪 | 内容 |

抽取判据（宁可不记）：
- 我说的：句子里要有将来时段词（明天/后天/今晚/等会/回头/下次/晚点/待会/一会儿）**且**有「为对方做点什么」的动词（陪你/给你/帮你/带你/一起/发你/讲给/让你/带你看/放给你）；
- 他说的：必须带硬语气（一定/肯定/说好了/我保证/答应你），否则「明天我去学校」这种日常陈述会被记成莫名其妙的账。

实测（副本单测 4 句：2 记 2 不记；生产端到端）：
```
POST /promise/add {"what":"（自测）答应他明天一起把那道题弄完","due_ts": now-120}
→ /context  sections.promise = 69
   【没结清的事】
   - 11月11日 16:26｜（自测）答应他明天一起把那道题弄完（刚到点）
   （别讨债：只影响语气，不要复述「你说好要…」）
POST /promise/close {"id":3,"state":"cancelled"} → /context 里块消失、list 清空
```
