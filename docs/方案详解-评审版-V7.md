## 一、这是什么，以及它不是什么

### 1.1 定位

「小鲸鱼数字生命卡」是一套**可搬迁、可审计、单机运行的长期对话体人格系统**。它不是一个聊天框，也不是一套 prompt 模板，而是一个带**持久记忆、情绪状态、时间感、身份连续性**的本地服务：

- 一张卡 = 一个目录，里面一个 `card.db`（SQLite）是全部记忆与状态，加一把钥匙（`seal.key`）、一份卡外锚（`anchor.json`）、若干缓存与检查点；
- 服务（`mind_server.py`）监听本机端口，把"这一次该给模型看什么"装配成一段上下文（`/context`），并把"这一轮发生了什么"写回记忆（`/report`）；
- 任何前端（DSH 插件、控制台、命令行桥、别的程序的 HTTP 调用）都只是这张卡的**门**，卡本身不依赖某一个前端。

系统的核心主张只有一句：

> **人格的连续性 = 记住的事 × 此刻的情绪 × 现在是什么时候 × 我是谁。**

四个乘数分别对应四套子系统：记忆（第三、七章）、情绪与身体（第五章）、时间与事件（第四章）、身份与账本（第六章）。

### 1.2 明确不做的事（非目标）

写清楚"不做什么"比写"做什么"更能说明设计取舍：

| 非目标 | 原因 |
| --- | --- |
| 不做多用户 / 多租户 | 一张卡服务一个人。多账号是"多扇门"，不是"一张卡里塞多个人"：同一个 `card.db` 可以被 QQ、控制台、DSH 同时接，但记忆与情绪只有一份。要隔离就复制一张新卡（`migration.fork`）。 |
| 不上云、不调第三方记忆服务 | 全部记忆、向量、情绪数据留在本地 SQLite；除对话模型本身外无外部依赖。 |
| 不做"删除即消失" | 删除在语义上是**撤回**而非物理销毁：见 §3.5、§11.3。 |
| 不做通用 RAG 框架 | 召回的打分、池子、衰减都是为"一个人几十年的记忆"调的，不是为文档问答调的；不追求通用性。 |
| 不追求"永不遗忘" | 遗忘是功能：容量无限增长会让检索成本与噪声一起爆炸（§11.4）。 |

### 1.3 硬约束

1. **单机单写者**：同一张卡同一时刻只允许一个进程写（`writer_lease` 租约 + 写闸），其它进程只读并显式返回 `409 / E_NOT_WRITER`。
2. **纯本地依赖**：Python 3.13 + SQLite + numpy；语义模型是 390MB 的 `bge-small-zh-v1.5`，用纯 numpy 前向（`embed_np.py`），不需要 torch 常驻。
3. **可搬迁**：整套状态都能随目录搬走（`tools/portable.py`），搬走之后靠"卡外锚"识别"这还是不是同一张卡、有没有被换成旧的"。
4. **每个结论要有账**：写入进时间线（`timeline`），定期盖章（`checkpoint`），卡外留锚（`anchor`）。任何"看起来对"都要能被三本账交叉验证。

## 二、总体架构

### 2.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层   DSH 插件(dsh-plugin) │ 控制台(console.py) │ CLI(bridge.py) │ MCP(whale_mcp.py) │ 任意 HTTP
├──────────────────────────────────────────────────────────────┤
│ 服务层   mind_server.py —— HTTP 路由 / 鉴权 / 请求 ID / 写队列 / 后台线程
│          ├ write-queue（唯一写者）  ├ world-tick（世界时钟） 
│          ├ maint（维护/对账）      └ boot-check（启动自检）
├──────────────────────────────────────────────────────────────┤
│ 心智层   card2.MemoryCard（门面）+ 一组纯模块
│          记忆 cardmix_store/cardtext/facts/poolmath/semantic/embed_np
│          时间 cardtime/tempora     情绪体感 body/padlib/viscera/hormone/emotion_link
│          联想与模式 synapse/impression/skill   驱力 motiv   上下文权重 ctxweight
├──────────────────────────────────────────────────────────────┤
│ 账本层   timeline（连续 hash 链）│ checkpoint（签名章）│ anchor（卡外锚）│ seal（钥匙）
├──────────────────────────────────────────────────────────────┤
│ 存储层   SQLite card.db（WAL）+ cache/pods.json + checkpoints/ + 备份目录
├──────────────────────────────────────────────────────────────┤
│ 运维层   disks（盘子/备份/主备）backup_verify  restore_drill  smoke  health_audit  versions  migration  device
└──────────────────────────────────────────────────────────────┘
```

依赖方向是**单向的**：接入层 → 服务层 → 心智层 → 账本层 → 存储层；运维层横向读各层，但不被任何一层 import。这条纪律由 `docs/懒import台账-V7.md` 和 `tools/smoke.py` 的"六模块独立 import"检查共同守住——心智层的纯模块（`padlib`、`viscera`、`motiv`、`vmath`、`poolmath`、`cardtime`、`body`、`cardtext`、`diag`）允许被单独 import，不依赖 `card2`。

### 2.2 一次对话的两个请求

系统没有"一个大函数包办一切"，而是刻意拆成**读一次、写一次**两个请求：

```
 用户说话
    │
    ▼
① GET/POST /context  { message }        ← 只读（默认不开全局锁）
    │  快反应：身体先对这句话有反应（viscera_touch / mood）
    │  装配：按 §7 的十六格拼上下文（人格→长期→最近→此刻想起→…→状态）
    │  返回：{ prompt, sections{16}, hits, scene, weights, est_tokens }
    ▼
 外部对话模型（DeepSeek 等）生成回复
    │
    ▼
② POST /report  { user_message, reply, source }   ← 唯一写入口
    │  进写队列（单写者）→ 拆句/抽取/落库/embedding/时间线/情绪结算/承诺抽取
    ▼
   返回 request_id；派生结果（embedding、consolidate）在锁内短事务后异步补齐
```

这样切的好处是：**读路径不写、写路径不拼上下文**。读慢了不影响写，写慢了不堵读（V7 的读写分离改造就是在把这条缝越做越开，见 §10.3）。

### 2.3 四本账

| 账本 | 位置 | 记什么 | 解决什么 |
| --- | --- | --- | --- |
| 时间线 `timeline` | `card.db` | 每件发生过的事：`seq/ts/kind/note/prev_hash/self_hash/writer` | "先发生了什么、后发生了什么"，hash 链防篡改 |
| 检查点 `checkpoint` | `checkpoints/` | 定期对"这张卡走到哪了"签名盖章 | 回滚检测（`live_head_seq`） |
| 卡外锚 `anchor.json` | 卡外 | 原库路径、时间线条数、链头、`device_id`、签名 | 识别"整卡被换成旧版本" |
| 备份 | 多处 | 一致性快照 + 完整性复核 | 灾难恢复（3-2-1） |

四本账的口径必须一致：`/health.reconcile` 每天对一次，任何一本对不上就亮红（`anchor_tampered`、`checkpoints_stale`、`backup_missing` 等）。

### 2.4 启动顺序与稳态

1. 读卡 → 拿写者租约（抢不到就只读启动，写接口全部 409）；
2. 迁移 schema（只加不删）、打开 WAL、读回 `journal_mode` 真值；
3. 起后台线程：`write-queue`（唯一写者）→ `world-tick`（默认 60s，推进情绪/内脏/时间）→ `maint`（维护、日结对账、WAL 阈值 checkpoint）→ `boot-check`（启动 6s 后跑六项自检）；
4. 启动自检结果挂到 `/health.boot`：`mem_rows / journal_mode / db_writable / pods{ready,cache_kb} / promise_table / world_tick / readonly`。

冷启动的代价主要是语义模型预热与舱（pod）构建；V7 把前者固定为一次性的几十秒，把后者改成"后台懒建 + `cache/pods.json` 落盘复用"（§10.3），稳态 `/context` 在 535–800ms。

## 三、记忆系统

记忆系统的核心指标不是「存了多少条」，而是「该想起来的时候能不能排上来」。这一章按写入、召回、粗筛、清理四条路径讲；所有阈值都标了 `文件:行号`，注释与实现不一致时以代码为准。

### 3.1 设计目标与不变量

三条不变量决定了后面的所有取舍。

**一、忘是检索行为，不是删除。** 一条记忆离开可见范围要经过 `mem → mem_archive → deep → trace` 四级下沉，只有最后一级 `_forget_row` 才真正 `DELETE`，而且它仍然先写 tomb、再把整行、细节 JSON 和向量抄进 `mem_archive`（`card2.py:4263-4290`；`cardmix_store.py:658-692`）。`mem_archive` 里的注释原话是「忘是检索行为，不是删除行为」。到了 `trace` 阶段，正文消失，只剩 `(day, region, count)` 的计数。

**二、池是可见度档位，不是四张表。** 同一行 `mem` 用 `pool` 字段表示当前档位。`archive` 默认被 `recall` 的 `WHERE m.pool != 'archive'` 排除（`card2.py:5692`），只能走字面的 `archive_search`；常规召回看不到它，但数据仍在。

**三、价值在写入时判，检索只负责排序。** 权重初值、区域、信任、事件时间都在 `remember()` 里定；召回阶段没有在线学习，只有去重续命、巩固、下沉三处会改状态。

四个池的进入与离开条件如下（`short` 是默认池，`cardmix_store.py:84`）：

| 池 | 进入条件 | 离开/下沉 | 时间常数 |
|---|---|---|---|
| `short` | 新记忆默认落这里 | 满 7 天且海马分 ≥0.35 沉入中期；分不够则留下继续淡，直到 `wn < CLARITY_GC(0.01)` 才删除 | 前 3 天 `LAM_S1=1.80e-6`（半衰期约 4.5 天），之后 `LAM_S2=1.50e-5`（约 12.8 小时）（`poolmath.py:23-31`、`:218-222`） |
| `medium` | 海马分 ≥ `THETA_MEDIUM(0.35)`；中期池存活下限 `W_FLOOR_MEDIUM=0.08` | 分 ≥0.60 且有「长期票」时升 long | `LAM_M=2.70e-7`，半衰期约 29.7 天（`poolmath.py:27`、`:223-224`） |
| `long` | 海马分 ≥ `THETA_LONG_STRICT(0.60)`、`_long_ticket_ok` 为真、且未被标脏；下限 `W_FLOOR_LONG=0.15` | 年龄 ≥365 天且 `wn < 0.02` 沉 archive | 前 90 天保护期，之后 `LAM_L=2.16e-8`，半衰期约 371 天（`poolmath.py:29`、`:191-195`） |
| `archive` | 从 long 下沉 | `wn < 0.002` 沉 deep | `K_ARCHIVE=1.5e-8`，约 535 天（`poolmath.py:225-226`） |

`deep`（`K_DEEP=3.0e-9`，约 2674 天）再往下才是 `trace`（`card2.py:3712-3779`）。短池的 7 天不是删除线，是结算点：V5.6.3 之后，满 7 天但分不够的记忆留在短池继续按自己的曲线衰减，不再「第七天一刀切」（`cardmix_store.py:556-575`）。短池也没有容量淘汰，`_evict_short_overflow` 已停用（`card2.py:3702-3710`）；四个池都不设条数上限。

### 3.2 一次写入的完整链路

`remember()` 在 `cardmix_store.py:79`，不在 `card2.py`。一次写入依次做八件事：

1. **剥壳与归一。** `strip_sysmark` 去掉系统工单外壳，空文本直接返回 `None`（`:92-96`）；群聊来源把 `salience` 压到 `GROUP_SAL_MAX=0.35`（`:101-105`）；`normalize_time` 以说话时刻为参照归一相对时间（`:110`）。
2. **拆句。** `split_memory(text)` 返回主干 `core` 和细节列表 `details`（`:112`）；细节按 `TIME / PLACE / EMOTION / NUMBER / ACTION / MODIFIER` 分类，各带一个基础权重（`cardtext.py:681-760`）。
3. **标注。** 情绪默认「命中情绪词 1.0，否则 0.25」（`:116-117`）；实体数取地点数加数字数，上限 5（`:119-121`）；`classify_region` 定事实/情节/自我/习惯/偏好/闲聊（`:125`）；`assess_trust` 给出信任、冲突标记和原因（`:144`）。
4. **去重。** 先做全表精确匹配 `raw=? AND region!=?`，要求非 flash、`trust >= TRUST_WARN(0.70)`、无冲突（`:167-183`）；否则与最近 200 条比字面 Jaccard，`>= DEDUPE_JACCARD(0.92)` 才算重复（`:184-202`，常量在 `cardcfg.py:28`）。命中后走「续命」：`_g = GAIN_REPEAT(0.10) × max(0, 1-wn)`，`w` 抬到 `min(W_CEIL_RECALL[pool], wn+_g)`，刷新 `t_anchor`、`access_count`、`recall_n`，细节权重加 `0.8×_g`，直接返回旧 id（`:203-229`）。
5. **定初值。** `w0 = (0.50 + 0.30×min(emotion,1)) × (0.75 + 0.50×surprise)`，夹到 `[0.20, 1.0]`；`trust < 1` 时再乘信任并保底 0.05（`:235-242`）。
6. **编码与时间分离。** 有语义层时 `encode(embed_text_for(text, speaker, core))`（`:263-268`）；`parse_event_time(text, ref_ts=at)` 单独解析「事情哪天发生」，解析不到留 0（`:278-283`）。这是 `event_ts` 与 `create_ts` 分开的原因：写下来的时刻不是事情发生的时刻。
7. **落库。** 一条 `mem` 写 30 列，`create_ts` 和 `last_active_ts` 都用 `at`（说话时刻），不是 `now`：

```python
# cardmix_store.py:284-294
_evts, _evprec = parse_event_time(text, ref_ts=at)
c.execute(
    "INSERT INTO mem(raw,core,vec,pool,w,t_anchor,salience,oxy,entities,"
    "emotion,create_ts,last_active_ts,region,subj,verb,obj,erase_stage,emb,"
    "speaker,mtype,trust,conflict,conflict_why,value,source,"
    "about_uid,about_layer,quarantine,event_ts,event_precision) "
    "VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?)",
    (text, core, json.dumps(vec, ensure_ascii=False), pool, w0, at,
     salience, oxy, entities, emotion, at, at, region,
     _subj, _verb, _obj, 0, _emb, speaker, mtype,
     _trust, _conflict, _why, _value, source or "",
     str(about_uid or ""), _lay, _quar, float(_evts or 0.0), _evprec or ""))
```

细节不是单独建表：它们以 `kind / text / weight` 写在 `detail` 里，权重按 `ww = wgt × exp(-k × dscale × age)` 计算，低于 `KEEP_DETAIL(0.02)` 直接不写（`:311-318`）。`k` 按类型给：TIME/NUMBER `4.5e-6`、MODIFIER `4.0e-6`、PLACE `3.2e-6`、EMOTION `1.2e-6`；`dscale` 按池给：short `1.0`、medium `0.25`、long `0.03`（`:256`）。所以同一句细节，在短池里三天就淡掉，在长池里几乎不褪。

8. **原文与旁路。** `inbox` 留一份原文（`kept=1`，`:296-307`）；`dialogue` 由 `add_dialogue` 另写，user 一条、assistant 用 `ts+1`（`:404-428`），`mem_id` 是逻辑外键、没有声明 FOREIGN KEY（`card2.py:2446-2452`）。原文不进向量库、不参与召回，只在 `/trace` 时用来翻原话。之后 `synapse.add_semantic_edges` 建联想边、`facts.record` 抽事实、`_invalidate_idf` 让下一轮重建 IDF（`:319-354`）。

### 3.3 一次召回的打分公式

`recall()` 在 `card2.py:5631`。它先用查询串算 IDF 加权向量 `qv`、字面键集合 `q_keys` 和语义向量 `q_sem`，再按池、时间窗、说话人、群聊做过滤：默认排除 `archive` 和 `dead/quarantine` 行（`:5685-5693`）；时间窗只收窄 `episode / flash / chatter / 空`，`fact / preference / self` 不参与，精确日期只留当天、`min_keep=1`，非精确留 `min_keep=5`（`:5707-5728`）。注释里记了代价：45 天档 ret20 召不回的 47 道题里，有 11 道是被时间窗误筛的。

真正在用的分数是四项加权（`card2.py:867`、`:5867-5868`）：

```
s0 = 0.35·blended + 0.30·cover + 0.20·wn + 0.10·recency
```

各项来源：

- **`blended`（语义）**：`0.75 × sem_best + 0.25 × sim`。`sem_best` 取「整句向量余弦」与「细节向量余弦 × `DET_REL(1.0)`」的较大者；两者都大于 0 时，再与 `0.5×(sem+det)` 取最大（`:5831-5836`）。`sim` 是查询与行向量的 IDF 加权余弦，行侧结果带缓存（`:4917-4945`）。
- **`cover`（字面覆盖）**：`|q_keys ∩ 行字面键| / |q_keys|`（`:5841-5842`）。
- **`wn`（还清不清楚）**：`weight_now` 按池、区、层级、关系层算出的当前权重（`poolmath.py:161-231`）；长池先扣 90 天保护期，core tier 不衰减。
- **`recency`（多久没提）**：`exp(-age_days / RECENCY_SLOW_DAYS)`，`RECENCY_SLOW_DAYS=45.0`（`:942-943`）。45 天前的事只剩 `exp(-1)=0.368` 的新近分。

```python
# card2.py:5845-5847, 5867-5868
wn = wn_row(r, now)
age_days = (now - r["last_active_ts"]) / DAY
recency = math.exp(-age_days / RECENCY_SLOW_DAYS)
# …
s = (SCORE_W[0] * blended + SCORE_W[1] * cover
     + SCORE_W[2] * wn + SCORE_W[3] * recency)
```

四项之后还有一层乘子，按命中情况叠加：

| 项 | 值 | 位置 |
|---|---|---|
| 同人 / 明确别人 | ×1.10 / ×0.92 | `card2.py:898-899`、`:5872-5877` |
| 显著度 | ×`(0.85 + 0.30×salience)` | `:5879` |
| 提问前 30 天内的 user 消息 | 最多 ×1.06 | `:938-940`、`:5881-5885` |
| 激素系数 | ×`1 + (f_end-1)×(0.5+0.5×oxy_w)` | `:5900-5901` |
| 命中目标分区 | ×`REGION_BOOST(1.25)` | `:859`、`:5902-5903` |
| 信任 / 冲突 | ×`(0.5+0.5×trust)`，冲突再 ×0.50 | `:5905-5913`、`:422` |
| 群聊 | ×`GROUP_RECALL_PENALTY(0.55)` | `:874`、`:5930-5932` |
| 问「你自己说过」 | self 话术 ×1.45（问名字 1.95） | `:878-880`、`:5934-5943` |

情绪加成 `EMOTION_RECALL_BOOST=0.25` 和第二阶段 rerank（`WHALE_RERANK=1`）默认都关（`:910-920`）；默认路径就是上面这一遍。分区路由先只在 `guess_query_regions` 给出的区里打分，不足 2 条才回退全库（`:5954-5960`）。

有一个实现与注释不一致的点要写清楚：`pin` 的「清晰度压到 0.5」是在 `s` 已经算完之后才改 `wn`（`:5916-5924`），所以它不影响排序分，只影响返回和 trace 里的 `wn`。排查「置顶为什么没排第一」时别按注释找错地方。

45 天档的根因不在衰减曲线。实测 45 天档 ret5 只有 57%、ret20 72%（`:914-917`），绝对数是 100/167 和 120/167（`:942-948`）；差的 15 个百分点，是「存住了却排不进前五」。错误分类里最大的一类是候选根本没进 top-k，占 42.8%（159 条事实口径里 68 条，`docs/升级修改总表-V7.md:492`）。所以 14 天改成 45 天不是主因，主因在候选集和排序。

### 3.4 舱（pod）粗筛

舱是把全库向量先聚成几堆，召回时只扫最近几堆。常量：`N_PODS=8`、`POD_KMEANS_ITERS=12`、`POD_MIN_ROWS=60`、`POD_TAKE=3`，开关 `POD_ENABLED=False`（`card2.py:966-980`）。

建舱用固定种子 `random.Random(20261030)` 做余弦 k-means，12 轮，质心取成员均值；少于 60 条就清空（`:5308-5373`）。另建一份语义质心，用 embedding 均值再归一化，路由时优先用它（`:5375-5409`）。过期条件不是「有新记忆就重建」，而是 `n - _pod_n >= max(20, n//20)`（约 5%，`:5294-5306`）。

缓存写在卡目录的 `cache/pods.json`（`:5411-5412`），内容是 `key / cents / pod_of / pod_sem`，`key = [建舱时条数, N_PODS, POD_KMEANS_ITERS, 语义维度]`（`:5428-5429`）。加载时 `key[0]` 必须等于当前 `SELECT COUNT(*) FROM mem WHERE vec IS NOT NULL AND vec<>''`，`key[1]/key[2]` 必须匹配常量，语义维度不符就丢掉 `pod_sem`；坏文件改名成 `.bad-<时间戳>` 留证（`:5446-5487`）。`_ensure_pods` 不在读请求里同步建舱：有旧舱就后台重建，冷启动也后台建，30 秒节流（`:5489-5524`）。首次全库扫描实测 8.9 秒，缓存就是为了把这个成本挪出请求路径。

**当前默认关闭**，原因写在 `:5564-5581`：查询「暑假工」的正确答案 id321 落在第 5 舱，按语义质心却排到第 8 舱，被 `POD_TAKE=3` 直接踢掉；8 个舱的相似度是 0.1998 / 0.1957 / 0.1956 / 0.1894 / 0.1797 / 0.1717 / 0.1566 / 0.1525，首末只差 0.05，分舱没有区分度。重开条件也写在旁边：库超过 5000 条、且舱相似度首末差大于 0.15。`_pod_candidates` 在收窄后不足 5 条时会放弃舱结果、回退全库（`card2.py:5767-5775`）。

### 3.5 净化与梦

**脏输出拦截。** `clean_store_text` 在 `cardtext.py:117-160`：剥 `<think…>` 块（无闭合就从 `<think` 截断）、控制字符、零宽字符，统一换行，超过 `STORE_MAX_CHARS=8000` 截断并加「……（截断）」。如果文本 ≤600 字又命中工具调用 JSON 的特征（`{"name" / "arguments" / "tool_call"`），直接返回空串并记 `rejected:tool_json`。`mind_server.py:1946-1947、2011` 在入库前调用它；`remember()` 自己还会再剥一次系统工单壳（`cardmix_store.py:92`）。

**归档检索。** `archive_search(query, k=3, min_score=0.22)` 用中文 bigram 算覆盖，要求至少命中 2 个 bigram 且分数 ≥0.22，按 `(-score, -create_ts)` 排序（`card2.py:4351-4395`）。它不是「当前召回为空才兜底」：`assemble_context` 每次都试一次，有命中才拼进上下文（`:7026-7050`）；注释说明，正常召回总能返回几条不相干的，用「有没有结果」判断该不该翻旧账会一直误判，所以改看内容实词。

**梦。** 待整理的是 `dialogue WHERE dreamed=0`；攒够 `DREAM_MIN_TURNS=40` 轮或空闲 `DREAM_IDLE_HOURS=6.0` 小时触发（`card2.py:447-448`、`:2907-2930`）。`dream_commit` 分五阶段（`:2978-3116`）：

1. `ingest`：丢弃空文本、少于 4 字的碎片、批内重复（`sig=txt[:48]`）；region 不在已知集合就回退 `R_FACT`；`salience` 默认 0.55、`w0` 默认 0.62。
2. `summarize`：逐条调用 `remember()`，来源标成 `dream:<key[:10]>`。
3. `link`：把本批写入的 id 记进批次。
4. `validate`：回查这些 id 是否真在 `mem` 里，丢失的记 `lost_after_write`。
5. `commit`：把这批 `dialogue.dreamed=1`，批次置 `done`。

幂等键是 `sha1(sorted(dialogue_ids) + 每条 text)[:16]`（`:2939-2949`）；重复提交返回 `duplicate` 而不重写。失败时批次置 `failed`、`attempts+1`，但**不翻 `dreamed`**，下一轮还能重压（`:3034-3046`）。

### 3.6 已知限制

- **全表向量余弦是 O(N)，没有 ANN 索引。** 每次召回都要把候选行的向量读出来算一遍；10 万条约 800ms（`card2.py:962-963`），`_vecs` 在 10 万条时约 1.3 秒、冷 IDF 约 8 秒（`:4947-4996`）。当前库只有千余条，这个成本可以接受；上万条后舱或外部索引会重新变成必选项，而舱现在因为分舱质量不够是关着的。
- **细节褪色是近似。** 每个细节只按 `kind` 给一个固定 `k`，再乘池子的 `dscale`、按写入年龄算（`cardmix_store.py:311-318`）；没有单条细节的访问计数，也不区分「这句话里的哪个词更重要」。TIME/NUMBER 的 `k` 是 EMOTION 的 3.75 倍，所以时间地点先淡、情绪最后淡——这是顺序近似，不是语义判断。
- **去重可能误合并。** 精确匹配是全历史 `raw=?`，Jaccard 只和最近 200 条比；同一句话隔一个月再说一次会被并进旧行，只涨权重，新语境和新细节不会补进去（`cardmix_store.py:167-229`）。反过来，`trust < 0.70` 的记忆不参与合并，低信任来源会产生重复条目。
- **可追溯率 84.6%。** 发布验收时 `mem` 1340 条里 1134 条能翻到原话，`dialogue` 1344 行，剩下 206 条本来就没有对话原文（做梦摘要、群聊导入、self 记录、脚本写入）（`docs/V7发布验收清单.md:35`）。`/trace` 对这 206 条只能显示「无原话」，不是查询失败。
- **两处实现债。** `pin` 的清晰度上限在打分之后才生效（`:5916-5924`），与注释描述不符；`cardtext.py` 里 `split_memory` 定义了两次（`:596`、`:681`），生效的是后一份，前一份是遗留副本。另外 `cardmix_store.py:147` 的注释还写着 Jaccard 0.72，实际常量是 0.92（`cardcfg.py:28`）。

## 四、时间与事件系统

这张卡里有两套时间，分别回答两个不同的问题：

- **事发时间**：这句话讲的事发生在什么时候。写入记忆时由 `parse_event_time` 解析，落到 `mem.event_ts` / `mem.event_precision` 两列（`cardmix_store.py:278-294`）。`create_ts` 是"这句话被记下的时刻"，`event_ts` 才是"事情发生的时刻"——「我昨天剪了头发」隔三天再问，只按 `create_ts` 筛会走错门。
- **约定时间**：这件事应该什么时候发生、到点没有、实际几点到。由 `tempora.py` 解析，落到 `tevent` / `tstate` 两张表。

两者不共用一个解析器。`cardtime.parse_event_time` 只认 `7:20` 这类 24 小时冒号写法（`cardtime.py:159`），因为记忆里的「三点」歧义太多，宁可标成「不知道哪天」也不猜；`tempora` 专门认「三点」「三点左右」「今晚三点」，并给出容差窗。这个分工是整个章节的前提：**记忆只记发生了什么，事件系统才管应该发生什么。**

### 4.1 约定时刻 vs 实际时刻

用户的核心诉求是：说「7:20 到校」，实际可能 7:10 多到，也可能 7:20 多才到。所以 `tevent` 里约定和实际是两组字段，不能合成一个时间戳：

| 字段 | 含义 | 写入位置 |
|---|---|---|
| `expect_time` / `expect_end` | 约定窗口（准点 ± 容差） | `tempora.py:513-514` |
| `actual_ts` | 实际时刻，可为 0（还没发生） | `tempora.py:517` |
| `reason` | 人可读的偏差，如「实际 07:38，早 2 分」 | `tempora.py:515-516`、`:577` |
| `meta` | 解析出的窗口 JSON（含 `base`、`tol_min`、`flags`） | `tempora.py:514` |

**一句话两个钟点。** 第一个当约定、第二个当实际，`add_plan` 直接分开存：

```python
# tempora.py:504-508
wins = all_clock_windows(s, ts)
if len(wins) >= 2:
    actual_ts = float(wins[1]["base"])
    delta = int(round((actual_ts - float(w["base"])) / 60.0))
    note = "  实际比约定%s %d 分" % ("晚" if delta > 0 else "早", abs(delta))
```

**事后补报。** `note_actual` 做的第一件事不是算差值，而是把「补报的钟点」贴到约定那天：取约定日 `±1` 天、横跨 `hh` 与 `hh±12` 的六个候选，选离 `meta.base` 最近的那个（`tempora.py:555-560`）。

```python
# tempora.py:556-560
cands = []
for h in (hh, hh + 12 if hh < 12 else hh - 12):
    for dd in (-1, 0, 1):
        cands.append(ed + dd * DAY + h * 3600 + mi * 60)
act = min(cands, key=lambda x: abs(x - base))
```

偏差相对**约定的准点** `meta.base` 算，不相对窗口起点（`tempora.py:527-528` 的注释写明了这条）。候选行来自 48 小时内 `status='pending'` 的约定，按 `_topic_tokens` 的二字重合度排序；`overlap<1` 跳过、`overlap<2` 且距约定超过 6 小时跳过、超过 18 小时跳过（`tempora.py:539-565`）。实测：约定 07:40，补报「我到学校了，七点三十八」→ `delta_min=-2`，`reason` 追加「|实际 07:38，早 2 分」，状态置 `done`。

### 4.2 准点基线 + 容差窗

识别顺序是先准点、后大时段：`resolve` 一进来先试 `_clock_window`，认不出才退回 `_RULES` 词表（`tempora.py:371-378`）。准点这一层有两个常量：`_TOL_EXACT=30`、`_TOL_FUZZY=60`（`tempora.py:168-169`），含糊词表 `_FUZZY` 是「左右/前后/大概/差不多/约莫/或许/左右吧」（`tempora.py:166`）。

```python
# tempora.py:290-291, 316-319
fuzzy = any(w in s for w in _FUZZY)
tol_min = _TOL_FUZZY if fuzzy else _TOL_EXACT
...
return {"start": base - tol_min * 60, "end": base + tol_min * 60,
        "base": base, "tol_min": tol_min,
        "label": "%s ±%d 分" % (_hhmm(base), tol_min)}
```

| 输入（以 2026-11-11 为参照） | 解析结果 | 依据 |
|---|---|---|
| `三点`（上午说） | 15:00 ± 30 分 | 无时段词时在当天 `{h, h+12}` 里取第一个将来的整点（`tempora.py:266-274`） |
| `三点左右` | 15:00 ± 60 分 | `_FUZZY` 命中（`tempora.py:166, 290-291`） |
| `今晚三点` | **次日** 03:00 ± 30 分 | `pm` + 晚上 + `h≤4` → `day_carry=1`（`tempora.py:253-256`） |
| `下午三点到四点` | 15:00–16:00，`tol_min=0` | 两钟点之间只剩连接词才算区间（`tempora.py:298-308`） |
| `三点多` | 03:00–04:00，单边一小时 | `"多"` 在钟点后两字内（`tempora.py:311-314`） |
| `7:20` | 先转成「七点二十」，再走同一套 | `_colon_to_cn`（`tempora.py:191-204`） |
| `7:20 到校` | 07:20，不再猜成 19:20 | 命中「到校/上学/上课/早读/集合/上班/升旗」时，`h<12` 不推 12 点（`tempora.py:268-270`） |

`resolve` 的 `kind` 有 `day / part / soon / no_time / need_ask / none` 六种（`tempora.py:362-363`）。只有能落到具体窗口的才进 `tevent`；`no_time`（改天、回头、有空）和 `need_ask`（月底、年底、年前）直接返回 `None`——**认不出就不记，不拿一个假日期占位**（`tempora.py:494-496`）。

口语里的模糊词也能给窗口，但精度只到"一段时间"：「待会儿/待会/一会儿」= 现在起 2 小时，「马上」= 15 分钟，「晚点」= 2–6 小时（`tempora.py:385-393`）。这些窗口只用于"有没有这件事"，不用于算早晚分。

### 4.3 tevent：从 pending 到 expired

`tevent` 的列在 `tempora.py:427-452`：`event_type`（`plan`/`state`）、`status`、`content`、`expect_time`、`expect_end`、`importance`（默认 0.6）、`subject`、`source`、`raw_text`、`meta`、`closed_ts`、`actual_ts`、`reason`，索引建在 `(status, expect_end)` 上。另有一张 `tstate(key, val, updated_ts)`，只放「我这会儿在哪」这类单值状态（`tempora.py:447-451`）。

| 状态 | 进入方式 | 代码 |
|---|---|---|
| `pending` | `add_plan` 写入 | `tempora.py:513` |
| `done` | `note_actual` 结账，写 `actual_ts` 与偏差 | `tempora.py:574-577` |
| `expired` | `sweep` 发现 `expect_end < now` | `tempora.py:591-611` |
| `cancelled` | DDL 注释里的保留状态，仓库内没有写入路径 | `tempora.py:432` |

`sweep` 由后台维护线程每 `WHALE_MAINT_SEC`（默认 600 秒）跑一次（`mind_server.py:3517, 3613-3623`），返回每条过期约定晚了多少小时。它只改状态、不删行，所以「昨天答应的事没做」还查得到。

读侧拼成一段固定格式的上下文块：

```python
# tempora.py:643-656
ps = self.pending(limit=limit, now=now)
if ps:
    lines = []
    for p in ps:
        w = {"start": p["expect_time"], "end": p["expect_end"], "kind": "part"}
        lines.append("- %s（%s）" % (p["content"][:40], fmt_window(w)))
    parts.append("【没到点的事】\n" + "\n".join(lines))
ex = self.recent_expired(now=now, limit=2)
if ex:
    lines = []
    for e in ex:
        late = max(0.0, (now - float(e["expect_end"])) / 3600.0)
        lines.append("- %s（已经晚了 %.0f 小时）" % (e["content"][:40], late))
    parts.append("【过了点没做的】\n" + "\n".join(lines))
```

`block_text` 的第一行永远是 `now_line(now)`——「现在是 2026-11-11（周三）晚上 18:01」。这一行看着最不重要，实际是整块的锚：没有它，「今晚/明早/待会儿」都没有参照物。`tstate["where"]` 有值时再补一句「我这会儿在：…」（`tempora.py:641-642`）。`pending` 最多 5 条、按 `expect_end` 升序；`recent_expired` 在块里固定取 2 条（`tempora.py:650`）。整块挂到 `assemble_context` 的 `sections["time"]`（`card2.py:7208-7220`），属于"每轮可能变、只影响语气"的尾巴块，不参与前缀缓存。

自动落账发生在 `remember()` 末尾：只要开了 `WHALE_TEMPORA`、且句子里有时间窗，就调 `add_plan`（`cardmix_store.py:389-398`）。用未锚定的原句 `_plan_src`，因为锚定后的日期会被当成新信息（`cardmix_store.py:93`）。

### 4.4 时间窗只筛 episode

检索侧拿到「上周」「11 月 3 号」这类查询时，`query_time_span` 先给一个区间，然后只对**事件类**记忆生效：

- 允许被切的区：`episode`、`flash`、`chatter`，以及空/`None`（`card2.py:5707-5761`，`_timed` 在 `:5720`）；
- `fact`、`preference`、`self`、`habit` 不参与时间筛。

理由是这几类的命题本来就"一直成立"：「他喜欢猫」「我叫小鲸鱼」不该因为问的是「上周」就被切掉；只有 `episode` 才有"发生时间"这个属性。`flash`（闪光灯记忆）和 `chatter`（闲聊）是还没定型的近事，放行是为了不把刚发生的事漏掉。

精确到天时按 `event_ts` 卡在 `[start, end]` 内，且至少保留 1 条；只知道"最近/这两天"这种粗窗口时，`last_active_ts` 或 `event_ts` 有一个落在窗口后即可，至少保留 5 条（`card2.py:5721-5758`）。`min_keep` 是兜底：注释里记着 45 天档的 47 道题中有 11 道被时间窗误筛，留几条总比整格空掉好。之后还会按「我说/你说」和群号再筛一次（`card2.py:5732-5752`）。

### 4.5 已知限制

1. **话题匹配靠二字重合。** `_topic_tokens` 取所有二字片，剔掉含时间词的片，再减掉「的了我是」等停用字（`tempora.py:325-334`）。这能防住「7 点」这种两边都有的词把不相干的话配到一起，但跨天/跨周时仍会误配；`note_actual` 又只看 48 小时内的约定（`tempora.py:539-543`），隔三天补报就结不上账。
2. **12 小时歧义没有根治。** 没有上午/下午锚点时，只在当天的 `{h, h+12}` 里挑第一个将来的整点（`tempora.py:266-274`），不会看明天。实测 07:16 说「我七点十五就到了」会解析成 19:15；一句话两个钟点时，第二个钟点只带前 4 字上下文（`tempora.py:346`），「到学校，我七点十五」丢掉了「到校」这个锚，`actual_ts` 同样落到 19:15，早晚差会错到 715 分甚至 1450 分。
3. **口语模糊词精度低。**「待会儿」一律 2 小时、「晚点」一律 2–6 小时（`tempora.py:385-393`），只能当窗口，不能当点。
4. **约定捕捉没有意图判断。** `_PLAN_HINTS` 定义了「说好/答应/记得/要/得」这组词（`tempora.py:455-456`），但仓库里没有任何调用点；`add_plan` 只看时间窗能不能解析（`tempora.py:494-496`）。实测「今晚吃什么」也会被记成一条 `pending`，靠 `importance` 排序和人工清理兜着。



## 五、情绪、身体与动机

这条链是单向的：**事件 → 心境 → PAD/激素/内脏 → 语气与行为**。上层能改下层的读数，下层不能反过来"演"一个情绪；唯一的上行通道是行为结果（动机、亲密度）和生理反馈。

### 5.1 三层结构

**第一层：事件 → 心境。** `mood_of_event` 把一句话折成一个效价 `E∈[0,1]`：正负词各数命中数，`amp=(0.16+0.05·min(pos+neg,4))·(0.9+0.2·emotion)`，正面取 `0.5+1.10·amp`，负面取 `0.5−0.80·amp`，一个信号都没有就返回 0.5（`body.py:259-274`）。然后按 `M←(1−k)M+kE` 混合，`K_MOOD=0.20`（`body.py:215, 276-280`）。

```python
# body.py:276-280
def update_mood(mood, e_event, k=K_MOOD):
    """心境混合更新：M <- (1-k)*M + k*E_event"""
    mood = max(MOOD_MIN, min(MOOD_MAX, mood))
    e = max(MOOD_MIN, min(MOOD_MAX, e_event))
    return max(MOOD_MIN, min(MOOD_MAX, (1.0 - k) * mood + k * e))
```

同一句话连着说，效果递减：半小时窗口内第 `n` 次，`k=K_MOOD/(1+0.5n)`；没有情绪词的句子用 `K_MOOD_NEUTRAL=0.03` 轻擦（`card2.py:523, 2317-2327`）。最后夹一道软限 `MOOD_SPAN=0.35`，一次会话里心境离 0.5 不超过 0.35（`body.py:217`；`card2.py:2330-2332`）。没人说话时按指数回归 0.5，`K_MOOD_HOME=0.10`（`body.py:225, 282-295`），按 `1−exp(−k·days)` 算半衰期约 6.9 天，长尾永远差一点回不满。

**第二层：心境 → PAD。** `pad_of` 把心境和四条激素（血清素/多巴胺/皮质醇/催产素）压成三维：`P=0.5·p_mood+0.5·clamp(p_life)`，`p_life=1.8·(sero−.6)+0.9·(dopa−.4)−1.6·(cort−.2)+0.5·(oxy−.5)`；`A=(0.6·dopa+0.4·cort−a₀)·3.2`，`D=(0.6·oxy+0.4·(1−cort)−d₀)·3.2`（`padlib.py:38-64`）。`SCALE=3.2` 是"激素推到满时接近 ±1"的标定（`padlib.py:24`）。2026-11-09 之前 P 只读心境这个慢量，导致 P 恒为 0，提示语永远说不出"心情好/差"，才改成现在的一半一半（`padlib.py:51-55`）。PAD 只用于显示和语气提示，不参与任何判定（`padlib.py:72-73`）。

**第三层：激素/内脏 → 语气。** 四条激素按 `h(t+dt)=h_base+(h−h_base)·e^{−λ·dt}` 回归，`LAM_H=0.05`，半衰期约 13.9 小时（`hormone.py:61, 112-117`）。基线不是常数，`HOUR_BASE` 按小时加偏移：8 点皮质醇 +0.08，11–17 点多巴胺 +0.08，15 点血清素 +0.06（`hormone.py:134-144`），可用 `WHALE_CIRCA=0` 关掉。事件先分成 A（亲密）/B（伤人）/C（低落）三组，再按组给增量：A 组催产素 +0.12、多巴胺 +0.10；B 组皮质醇 +0.15、血清素 −0.12（`hormone.py:169-235`）。

出口在 `_state_line`：心情偏离 0.5 超过 0.04 就说「现在心情X」，催产素三档说「跟他很亲/挺熟/还在熟悉他」，再补一句 PAD 或激素给的说话倾向，两小时内被 A/B/C 事件戳过就补「刚才被暖了一下/刚才那句还有点堵/刚缓过来一点」（`card2.py:6428-6472`）。它只给状态、不给命令——「话多一点」比「请活泼一点」有效，后者模型会照着演（`card2.py:6446-6450`）。数值本身从不进模型，`describe()` 只吐人话（`emotion_link.py:22`；`viscera.py:345-406`）。

### 5.2 情绪词表与 mood_text

词表是两张短表：`NEG_WORDS` 收「难受/考砸/焦虑/压力/孤独/撑不住」等，`POS_WORDS` 收「开心/真好/厉害/哈哈/谢谢/抱抱」等（`body.py:251-258`）。2026-11-10 扩过一遍，原因是原来的二十来个词不认「真好/焦虑/压力」这些最常说的，绝大多数句子都被判成中性（`body.py:248-250` 注释）。

`mood_text` 是六档标尺，阈值是下界，取最后一个 `<= m` 的档（`body.py:297-318`）：

| 下界 | 读作 |
|---|---|
| 0.00 | 很低落 |
| 0.20 | 有点闷 |
| 0.38 | 平静 |
| 0.56 | 心情不错 |
| 0.74 | 挺开心 |
| 0.90 | 特别高兴 |

**自己的回复不推心境。** 调用点只有一处，且带 `speaker != "self"` 的闸（`cardmix_store.py:156-157`）。理由不是省算力：心境记的是"我身上发生了什么"，自己说的话不是发生在我身上的事；否则自夸、自我安慰、复述他的好话都会把读数刷高，这个数就不再是反应，而是自评。

### 5.3 内脏：24 个变量的刺激来源

`viscera.py` 维护 24 条 0–100 的慢变量，基线在 `viscera.py:45-52`，半衰期从去甲肾上腺素 1.2 小时到促性腺激素 200 小时（`viscera.py:55-62`）。它们不是装饰：`body()` 用交感/副交感加去甲、组胺算出心率、呼吸、体温、脸色、紧张度（`viscera.py:299-324`），`describe()` 再把读数翻成「耳尖有点烫」「心跳快了一拍」这种最多三句的人话。

刺激表 `STIMULI` 共 14 种，每种给一组（交感增量, 副交感增量, 激素增量）：

```python
# viscera.py:193-198
"cold":      (0.35, 0.0, {"cort": 8, "kyn": 6, "dopa": -6, "oxy": -2, "adh": 6}),
"criticize": (0.50, 0.0, {"cort": 12, "nora": 10, "sero": -4, "dopa": -5, "testo": 5, "adh": 3}),
"reject":    (0.45, 0.0, {"cort": 14, "kyn": 9, "dopa": -9, "oxy": -3, "adh": 9, "testo": 3}),
"comfort":   (0.0, 0.55, {"endo": 10, "dop": 6, "gaba": 8, "cort": -6, "npy": 5, "ofq": 9, "enk": 6, "cck": 4, "gh": 3}),
"apology":   (0.0, 0.45, {"endo": 7, "oxy": 3, "cort": -5, "ofq": 4, "enk": 3}),
```

`adh`（渴着等被找）、`cck`（收束）、`gh`（夜里修复）、`ofq`（内源平静）、`enk`（愉悦）、`testo`（竞争）这六个变量在 2026-11-10 之前没有任何输入，是"推不动"的死变量；现在被冷落、拒绝、安抚、道歉、深夜、被逗这些刺激接上了（`viscera.py:180-182` 注释）。慢变量只吃 0.4 的增量，一句话改不掉三天的底色（`viscera.py:208-227`）。

**`why` 字段（2026-11-11 新增）。** `viscera_hist` 原来只有数值，曲线能看出"变了"，看不出"被什么弄变的"（`card2.py:1686-1688`）。现在每个采样点带一条原因，三种取值：

| 取值 | 写入点 | 含义 |
|---|---|---|
| `talk:<原话前 120 字>` | `card2.py:1912` | 一句话进来触发的 |
| `stim:<刺激名>` | `card2.py:1962` | 控制台/测试手动戳的 |
| `idle` | `card2.py:1807` | 定时采样，没人说话，只做衰减 |

落库在 `card2.py:1798`（`[:120]` 截断），5 秒一格、force 时 2 秒（`card2.py:1715`），只留 7 天（`card2.py:1800`）。

### 5.4 印象层与动机层

**印象层**记的是「谁，在什么情境下，常做什么反应」，三个挂钩是主体 × 场景 × 反应（`impression.py:13-20`）。合并键 `react_key` 在 2026-11-10 改过：短句先判 12 类行为（回来/走/晚安/早安/亲近/吃饭/忙/累/低落/开心/谢谢/对不起，`impression.py:92-105`），有类时**只按 `subject + scene_mood` 找行、同类合并**，时段不参与匹配、只刷成最近一次：

```python
# impression.py:281-285
cur.execute(
    "SELECT id, n, alt_n, w, status, reaction, react_key, scene_event"
    " FROM impression"
    " WHERE subject=? AND scene_mood=?",
    (subject or "", sb[2]))
```

不改的话，「早上回来」和「晚上回来」是两行，一个口癖要连着一周在同一时段说话才凑得够 3 次；真卡上 150 行里带类的只有 1 行，提示一直为空（`impression.py:276-280` 注释）。`hint_lines` 的主门槛是 `weight_of(3)≈0.29`，但 **n=2 也说话**，只是换措辞「他好像老说」，门槛放宽到 0.12（`impression.py:488-515`）。权重 `W=1−0.5^{n/6}`，n=2 时 0.206、n=10 时 0.68，饱和但永不到 1（`impression.py:56-59`）。每个主体最多 40 条（`impression.py:77`），且只记别人的话——自己的技术日志曾被记成"他常说"（`cardmix_store.py:358-364`）。

**动机层**是七条驱力（好奇 .52、依恋 .55、胜任 .42、玩耍 .34、关心 .48、休息 .30、秩序 .38），各有半衰期（`motiv.py:40-48`）。`bump` 的默认语义是"满足/消耗"即**减**，并压了 0.15 的地板：不加地板，聊十几句依恋就归零、要五小时才回来（`motiv.py:100-115`）。「想念」用目标式而不是每跳累加——目标 = 基线 + `min(cap, idle_h·rate)`，只补差额：

```python
# card2.py:1534-1539
for _k, _cap, _rate in (("attachment", 0.30, 0.025),
                        ("care", 0.22, 0.018)):
    _tgt = float(motiv.DRIVES[_k][0]) + min(_cap, _idle_h * _rate)
    _cur = float(self.mo["d"].get(_k) or 0.0)
    if _cur < _tgt:
        self.mo["d"] = motiv.itch(self.mo["d"], _k, _tgt - _cur)
```

依恋最多顶到基线 +0.30（约 12 小时加满），关心 +0.22。`motiv_tick` 在每轮上下文的 tick 里跑，60 秒节流（`card2.py:3291-3296`）；产出 reach_out / learn / tidy / play / care_check / rest 六种候选，再由 `arbitrate` 做硬否决（风险 ≥0.7、上课、安静、距上次开口不足 1 小时、当天已主动 4 次），按紧迫度降序、成本升序取第一条（`motiv.py:233-281`）。

### 5.5 已知限制

1. **衰减曲线与戏剧性。** 单句最大 `amp≈0.36`，正面最多把 E 推到 0.94；乘 `K_MOOD=0.20` 后，心境单句最多动约 0.09，再加 0.35 软限。好处是一句话翻不了脸，代价是真被伤到时也要连续几次才显形；回归是指数的，永远不会精确停在 0.5（`body.py:282-295`）。
2. **内脏之间的耦合只是近似。** `regulate` 是一组手写 if：CCK 压多巴、GABA 压去甲、皮质醇 >45 压多巴/催产/促性腺/内啡肽、催产↔多巴正反馈（`viscera.py:231-295`），不是药理模型；`inject` 还限了单轮最多动基线的 15%（`viscera.py:433-471`）。它能保证"不暴涨、不顶死"，但不能保证生理上正确。
3. **印象样本少时噪声大。** n=2 的权重只有 0.206，提示语用「好像」是诚实的，但两次同现也可能只是巧合；真卡历史上有过 144 条里 140 条 n=1 的阶段，正是靠行为类合并才长出模式（`impression.py:83-87`）。
4. **词表匹配不处理否定。** 实测「今天不开心」→ `0.719`「心情不错」，因为 `POS_WORDS` 里的「开心」被当子串命中，没有否定判断（`body.py:259-262`）。这是词表法的边界，不是随机误差：否定句会稳定地往反方向推。


## 六、身份、锚与时间线

一张卡会变老、会搬家、会被复制。它必须能回答三个不同的问题：**卡里的记录有没有被改**（完整性）、**这份库还是不是原来那份**（同一性）、**这次加载的是谁、哪张卡、哪台机器**（三元）。这三件事分别由时间线、检查点/卡外锚、身份三元组回答，任何一件都替代不了另外两件。

### 6.1 卡外锚：哈希链证明不了「整卡被换」

`timeline` 的每一行都带 `prev_hash` 和 `self_hash`，改一行就会让后面所有行对不上。但这只防「卡内篡改」：如果有人把整个 `card.db` 换成三天前的快照，那张旧卡在自己的坐标里完全自洽，`verify_chain` 照样返回 `ok`。链防篡改，不防替换——`anchor.py:4-14` 的注释把这件事写得很直白。

所以需要一个**卡外**、且被签名保护的「这张卡长到哪儿了」。`anchor.json` 存这些字段（`anchor.py:341-354`）：

```
version      锚格式版本，当前 ANCHOR_VERSION = 1
device_id    签这份锚的机器（device.py 派生）
db           卡的绝对路径
count        timeline 行数
head_seq     链头 seq
head_hash    链头 self_hash
last_ts      链头时间
updated_ts   锚写入时间
sig          HMAC-SHA256(body 去掉 sig)
```

签名密钥是卡目录里的 `anchor.key`（`seal.load_key`，`seal.py:20-37`），签名对象是 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 的规范形式（`seal.py:40-41`）。读锚时先重算签名，对不上直接判 `anchor_tampered`，根本不看里面的数字（`anchor.py:192-207`）——先信钥匙，再信账。

锚存两份：卡内 `<card>/anchor.json`，卡外 `~/.dsh/anchors/<sha256(卡绝对路径)[:16]>.json`（`anchor.py:61-98`）。比对时取 `(count, last_ts)` 更大的那份（`_best_anchor`，`anchor.py:155-168`）；写入先本地、后卡外，卡外失败只在返回值里带 `err`，不阻断正常聊天（`anchor.py:355-362`）。

判定顺序就是「回滚比替换更早报警」（`anchor.py:208-250`）：

```python
if a_seq and c_seq and c_seq < a_seq:          # ① 链头序号倒退
    return {"verdict": "rollback", ...}
if state["count"] < a_count:                    # ② 条数变少
    return {"verdict": "rollback", ...}
if state["count"] == a_count and a_hash and state["head_hash"] != a_hash:
    return {"verdict": "replaced", ...}         # ③ 条数一样、头不一样
if (state["count"] > a_count and a_seq and c_seq
        and c_seq <= a_seq and state["head_hash"] != a_hash):
    return {"verdict": "replaced", ...}         # ④ 变多了但不是接在原来那条链后面
```

`first` 表示锚还没建立，`no_card` 表示库不在；CLI `python anchor.py check` 用退出码 0/1/2 分别表示正常、回滚或被换、首次（`anchor.py:365-379`），可以直接挂进启动脚本和巡检。

卡外锚这一层的价值不在「更安全」，而在**把不可判的事变成可判**：单看库，一份旧快照和一份活卡完全同构；只有卡外还记得「它曾经到过哪里」，回滚才会留下痕迹。

### 6.2 三本账：链、检查点、锚各管一段

| 账 | 落在哪 | 谁写、多久一次 | 回答什么 | 坏的时候报什么 |
|---|---|---|---|---|
| `timeline` | `card.db` 的 `timeline` 表 | 每次写入都 append；心跳 600s、启动一条 `boot` | 卡内记录是否连续、有没有被改 | `chain_bad`；链头 writer 不是自己时抛 `ForeignWriter` |
| `checkpoint` | `<card>/checkpoints/LATEST.json` + `CKPT-<seq>-<ts>.json` | `maint` 每小时（`WHALE_CHECKPOINT_SEC=3600`），留最近 40 份 | 某个 seq 时刻的签名证词：identity/instance/链头/各表条数 | 「卡被回滚过」「检查点记的是另一张卡」「没有签名密钥」 |
| `anchor` | 卡内 `anchor.json` + 卡外 `~/.dsh/anchors/…` | 每次 append 后 `_touch_anchor`，同链头 30 秒节流 | 跟卡外比：有没有变短、有没有换头 | `rollback` / `replaced` / `anchor_tampered` |

三者的关系可以压成一句话：**timeline 保证卡内自洽，checkpoint 把「自洽」钉在某个时刻并签名，anchor 把「钉住的那个时刻」搬到卡外。** 要伪造一次回滚，得同时改链（被 `verify_chain` 抓）、删检查点（被 anchor 抓）、改锚（没有 `anchor.key` 签不出来）。检查点校验读的是实时的 `SELECT MAX(seq) FROM timeline`，不信 `PORTABLE-MANIFEST` 里的旧 `head_seq`（`checkpoint.py:175-194`），避免拿一份过期的「证词」证明自己没问题；`KEEP=40` 只轮转旧件，`LATEST.json` 与每份 `CKPT-*.json` 都是 tmp+fsync+`os.replace` 原子落盘（`checkpoint.py:120-148`）。

时间线的「唯一」不靠数据库约束，靠写者自觉加一道检查：每一行都记 `writer`（`w-` + uuid 前 12 位，存 `~/.dsh/writer-id.txt`），`append()` 先看链头是谁写的，不是自己就抛 `ForeignWriter`，除非调用方显式 `allow_foreign`（`timeline.py:60-86, 170-174`）。`_last_row` 也不做缓存，每次都重查，避免两个实例拿着同一份旧链头去撞 seq（`timeline.py:154-161`）。

### 6.3 identity_id / instance_id / device_id：三个问题，三个答案

| 字段 | 回答 | 取值 | 什么时候变 |
|---|---|---|---|
| `identity_id` | 是谁（同一个角色） | `core_zone.identity_id` 优先，其次 `identity.json` 顶层（`disks.py:514-552`） | `fork` 时新生成；`migrate` 不变 |
| `instance_id` | 这一次加载的是哪张卡 | `"WG-" + timeline 第一条 self_hash[:8]` | 换一张卡才变 |
| `device_id` | 哪台机器 | `"dev-" + sha256(seed)[:16]` | 换机器才变 |

`instance_id` 取**最早**那条（`seq=1`）而不是最新：第一条是出生那条，写死之后不再动；取最新会每写一条就换一个「实例号」，那就不叫实例了。代码里这句注释和实现都在 `mind_server.py:3374-3381`，`disks.card_fp` 也用同一口径（`disks.py:144-146`）。

`identity_id` 在旧卡上可能是空串——`identity.py` 目前只封了六条锚的 sha256，卡里还没有独立的身份字段，`disks.py:517-520` 明确说「空串表示卡里还没有这个概念，不是这里算不出来」。`fork` 之后才会由 `mint_identity` 生成 `id-<父标识前20>-<uuid8>`（`migration.py:386-391`）。

`device_id` 的种子依次取 Windows `MachineGuid`、`/etc/machine-id`、`/var/lib/dbus/machine-id`，最后退回 `COMPUTERNAME|安装目录`，落盘到 `device.json`（`device.py:23-72`）。它不采集硬件序列号；读不到也不让启动失败。

`same_device` 是 `/health.node` 里的一个只读判定：当前 `device_id` 是否等于本地锚里记的那个（`mind_server.py:3369-3370`）。它的用途不是拦截，而是**让人看见**：整盘拷到另一台机器时，读的人应该知道「这台不是原来那台」，而不是被静默接受。真正会拦写的是租约和写者纪元，不是这一位。

### 6.4 CORE / LIVE：哪些东西不许顺手改

CORE 区住两类东西。第一类是六条身份锚：`user_qq`、`user_nickname`、`card_name`、三条底线（`identity.py:27-34`），每条一个 sha256。第二类是 `persona`（性格）和 `self_narrative`（自述）——它们同样住在 `core_zone`，但**不参与**那六条哈希，靠触发器 `trg_core_no_update` / `trg_core_no_delete` 物理挡住 UPDATE 和 DELETE（`identity.py:111-122`）。`seal()` 重建锚时会先把这些非锚字段抄出来、重建完再放回去，避免「盖个章把人设静默删了」（`identity.py:156-164`）。

LIVE 区是 `live_zone` 的 key/value，`set_live` / `get_live` 直接写（`identity.py:399-411`），放会随日常变化的状态。判断标准很简单：**删掉它，这个人还是不是原来那个人？** 是，就进 LIVE；不是，才进 CORE。

`set_persona(text, force=False)` 是 CORE 区里唯一开着的写口：显式拆掉两个触发器 → `INSERT OR REPLACE` → `commit` → `finally` 里无条件 `_init_schema()` 把触发器装回（`identity.py:219-243`）。`force` 目前是占位参数，没有确认闸，调用即写；注释写明了它是给将来「确认要改性格吗」留的（`identity.py:227-228`）。破坏性最大的是 `seal(values, force=True)`：已封的卡要覆盖，等于「我确认要换一个人」，会重写六条锚（`identity.py:132-149`）。

### 6.5 migrate 与 fork：搬家不是复制

`migrate` 是**同一张卡换地方**：`identity_id` 不变；落地由 `portable.py` 接管，`bump_writer_epoch` 把纪元加一、写 `TAKEOVER-DONE.json`（`portable.py:1167`，`disks.py:700-720`）；源盘 `retire_source` 写 `RETIRED.json`，源卡下次启动读到它就只读（`migration.py:53-58, 317-374`）。这是「一个我，换了个住处」。

`fork` 是**从这张卡分出一张新卡**：源盘不退休，新卡的 `identity_id` 由 `mint_identity` 新生成，并写三处——`identity.json` 顶层的 `identity_id`/`forked_from`/`forked_at`、`core_zone` 里一行 `identity_id`（优先级更高，而且不会被 `save_card()` 重写抹掉）、以及 `IDENTITY-FORK.json` 分叉凭证（`migration.py:394-463`）。两条链从此各写各的，谁也不是谁。

两种模式都往时间线记事件：`migration.started`、`migration.completed`、`migration.failed`、`identity.transferred`、`identity.forked`（`migration.py:36-45`）。`note` 是「人话｜JSON」两段，全角竖线分隔，正常文本里不会出现（`migration.py:60`）。`append_migration_event` 写完会只读复核整条链：写之前就断的，保留事件并抛 `ChainBroken(pre_existing=True)`，交给人处理；写之后才断的，回滚刚写那条（`migration.py:247-314`）。宁可炸，也不让账本悄悄变成两截。



## 七、上下文装配（/context 到底给模型看什么）

这是整个系统最核心的一段代码：`card2.py:6608 assemble_context`。它决定"这一轮模型看到的世界"。

### 7.1 十六格与顺序（顺序本身就是设计）

装配结果按 `sections` 分格，顺序固定：

| # | 格 | 内容 | 为什么在这一格 |
| --- | --- | --- | --- |
| ① | `identity` | 人格（`core_zone.persona` + 说话风格禁令） | **永不变**，放最前构建缓存前缀 |
| ② | `longterm` | 长期池里"值得一直记得"的事实/自我/偏好/习惯 | 同样稳定；情景不进这一格（那是"想起"的料） |
| ③ | `l0` | 时间线最近发生的事 | 与 ④ 共用 `recent` 配额："最近在聊"与"最近发生"是一件事的两面 |
| ④ | `recent` | 最近几轮原话 | — |
| ⑤ | `fact` | 事实块（谁/什么/现在什么状态） | **V5.8 实测**：事实块放最后时模型不看，挪到"想起"之前，同一批题 10/20 → 12/20 |
| ⑥ | `recall` | 此刻想起（向量召回 top-k） | 最不稳定的内容集中在尾巴 |
| ⑦ | `archive` | 冷档兜底（`archive_search`） | 只在"想不起来"时补一击 |
| ⑧ | `skill` | 程序性记忆（怎么做一件事，SM2 调度） | — |
| ⑨ | `viscera` | 身体状态（激素/内脏摘要） | 影响语气，不影响事实 |
| ⑩ | `impression` | 印象（"他在什么情况下会做什么"） | — |
| ⑪ | `motiv` | 驱力（好奇/亲近/胜任/玩/照料/休息/秩序） | — |
| ⑫ | `worklog` | 最近在做的事 | 让"施工中"的上下文不丢 |
| ⑬ | `dream` | 梦层摘要 | 低频、低配额 |
| ⑭ | `time` | 【现在/没到点的事/过了点没做的】 | 时间感的入口（§4） |
| ⑮ | `promise` | 承诺账本【没结清的事】 | 只影响语气，不允许"讨债"（§4.4） |
| ⑯ | `state` | 状态句（心情/亲密/话多话少） | **最后一个**：它是唯一每轮都变的句子，放尾巴只截断尾巴的缓存 |

顺序背后有一条硬规则（`card2.py` ① 的注释，2026-11-05）：

> 一句会变的话，把整段上下文变成了"每轮都是新的"。
> 修法：人格格只放不变的东西，状态那句挪到最后单独一格。现在顺序是 稳 → 稳 → 变 → 变 → 变。

也就是说，**缓存命中率是架构约束，不是优化选项**：任何新增内容都必须回答"我是稳定的还是每轮变的"，稳定内容进前面，会变的进尾巴。

### 7.2 配额：先算预算，再决定端几条

每格有配额（`est_tokens` 总量约束下按格分配）。召回格不固定条数，而是**配额驱动**：先算"这一格最多能放几条"，再"端到预算用完为止"（V5.9-A）。历史教训写在代码里：

- `WIDE_TOP_K = 5` 时加宽臂与普通臂完全等价，等于空转；
- 真卡这一格预算 4249 token、bench 中位 ~1500 token，预算根本没花完 —— 排到 6–12 名的答案是被**渲染层**扔掉的，不是没召回。

所以召回宽度是 `min(cap, RECALL_NARROW_MAX=6)` 起的配额函数，而不是一个常数。

### 7.3 召回的三次取数（同一格内）

1. 原句向量召回一次（保语义）；
2. 实词/多跳再召一次（保字面，分散在几条聊天里的线索，一条向量拼不回来）；
3. 按 id 合并去重后按分数排序，只渲染前若干条。

`V7 第 8 件`起加**召回 trace**：只在真装配上下文时记录（`recall_trace`），bench 的裸 `recall` 不记，避免测量污染。

### 7.4 装配是"快反应"之后的事

`assemble_context` 第一句注释就是：

> 快反应层：先让身体对这句话有反应，再拼上下文（顺序就是人的顺序）

也就是 `viscera_touch(text)` 先跑，情绪/内脏先动，再决定"这一刻我是带着什么情绪去看这些记忆的"。人格格、长期格、召回格的选择都会受当时状态影响（例如心情差时长期格的语气、motiv 影响"话题倾向"）。

### 7.5 失败与降级

- 召回为空：`recall` 格不出现，不报错；
- 舱未构建：`_pod_candidates` 返回 None 时退化成全表打分（正确性不变，只是慢）；
- 写端不可用：`/context` 仍可读（租约只读时读接口照常），但延后记账会跳过并记 `_defer_q` 丢弃计数；
- 任何一格算不出：该格返回空串，`sections` 里记 0，**不抛异常**（一段内容缺失不能把整轮对话打死）。

## 八、接口、通道与接入

### 8.1 拓扑与三条硬约束

这张卡只有一个对外入口：`mind_server.py`，默认监听 `127.0.0.1:8848`，说的是 HTTP/1.1 + JSON。命令行桥、DSH 插件、MCP 壳都是它的客户端，控制台页面也由它直接吐出来——没有第二个写库的人。

三条约束在代码里是硬的，不是文档口号：

1. **只认本地。** `_LOCAL_HOSTS = {"127.0.0.1","localhost","::1","[::1]",""}`（`mind_server.py:955-971`），`Origin`/`Referer` 来自别的 host 直接 403 `cross_origin_blocked`；`OPTIONS` 回 405 且不带 CORS 头，浏览器跨站连门都进不来。
2. **单写者。** 所有写操作排进 `queue.Queue(maxsize=256)`，由一个 `write-queue` 线程顺序执行（`mind_server.py:395-405`、`733-808`）。别的进程只能发 HTTP，不许自己开 `card.db`——两个进程同时开 WAL 会互踩，`dsh-plugin/lib/card.js` 文件头写得很直白。
3. **失败就说失败。** 每个错误都有 HTTP 状态码 + `error` + `code`，`/health` 里还能看到写闸拦过几种路径。没有「吞掉异常假装成功」的分支。

启动方式一行：

```bash
python mind_server.py --port 8848 --db card.db
```

`VERSION = "1.0"`、`DEFAULT_PORT = 8848`、`DEFAULT_DB` 都在 `mind_server.py:237-239`。`/health` 只回一行摘要，探活、看链、看锚、看语义层维度是否对齐，一次就够。

### 8.3 两种请求体，一个响应信封

**`/context`——只要一句话。**

```json
{"message": "我回来了", "recent": [{"role":"user","text":"..."}], "budget": 6000}
```

`message` 必填、`strip()` 后不能为空（空则 400 `empty_message`），超过 `MAX_TEXT = 20000` 字回 413（`mind_server.py:1738-1746`）。`recent` 允许三种形态：消息数组、条数（MCP 与插件传的就是条数，服务端自己查 `/recent`）、不传；`budget` 是这一轮的一次性总预算，不传就听卡里 `runtime_config` 的 `BUDGET`。

**`/report`——他说了什么、我回了什么。**

```json
{"user_message": "我回来了", "reply": "嗨，在呢", "source": "cli", "ts": 1763000000.0}
```

`user_message` 为空 → 400 `empty_message`；两段文本都过 `card2.clean_store_text`，命中「系统标记/工具残留」这类脏文本会 400 `dirty_output` 并把 `problems` 一并回给你（`mind_server.py:1939-2001`）。`source` 默认 `chat`。

其余接口的常用字段，一张小表够用：

| 字段 | 出现的接口 | 说明 |
|---|---|---|
| `text` | `/remember`、`/intake`、`/voice_say` | 要记/要合成的内容；空 → 400 `empty_text` |
| `pool` | `/remember` | 只认 `short`/`medium`/`long`，其他 400 `bad_pool` |
| `salience` | `/remember` | 重要度，默认 0.55 |
| `region` `speaker` `about_uid` | `/remember` | 分区 / 谁说的 / 关于谁 |
| `query` | `/recall`、`/ctx_preview` | `/ctx_preview` 只截 500 字试算，不落库 |
| `top_k` | **只 `/recall`** | 默认 5；桥与插件传 8（`/ctx_preview` 不认这个字段） |
| `overrides` | `/ctx_preview` | 覆盖六维权重，只算不写 |
| `n` `max_chars` | `/recent` | 默认 12 条、2000 字 |
| `id` 或 `mid` | `/trace`、`/forget`、`/mem/release` | 记忆 id |
| `items` `dialogue_ids` `key` `force` | `/dream/commit` | 摘要条目、原文 id、幂等键 |
| `path` `confirm` | `/disks/*` | 目标目录 + 显式确认 |
| `key` `value` `reset` | `/config` | 参数名 + 值；`reset` 删回默认 |
| `action` `dry` | `/cardslot` | 只认 `inject`/`unload`/`status` |
| `seconds` `confirm` | `/tick` | 快进秒数；>3600 且无 `confirm` → 403 |

**响应信封**：成功 `{"ok": true, ...}`，失败 `{"ok": false, "error": "...", "detail": "...", "code": "E_..."}`。每个回包都有 `request_id` 和 `ms`，响应头也带 `X-Request-Id`（`mind_server.py:1101-1125`）。`code` 只有在 `ERROR_CODES` 里登记过的 `error` 才有专属值，其余一律 `E_UNKNOWN`——所以客户端判断错误时**先看 `error` 字符串，再看 `code`**，别只认 code。

### 8.4 写闸、租约与 request_id

**为什么会有 409。** 卡的写者身份靠一份租约（lease）决定：`Mind.__init__` 里 `disks.acquire_lease()` 拿不到，就把自己标成 `readonly = True`（`mind_server.py:406-424`）。只读进程不退出——照样服务 `/health` 和所有读接口，只是不敢写。任何 `POST/PUT/DELETE` 只要不在 `GATE_READ_POST = {"/context","/recent","/recall","/ctx_preview","/trace"}` 里，就回：

```json
{"ok": false, "error": "readonly_lease_held", "code": "E_NOT_WRITER",
 "holder": "...", "holder_detail": "...", "path": "/report",
 "detail": "本进程是只读的（...）；要写就等另一份退出，或先关掉它"}
```

用 409 而不是 503，理由在注释里：503 会让客户端以为「服务挂了，重试」，409 说的是「服务好的，但这份不敢写」——重试没意义，该去找那个持有者。

除了租约，还有第二道闸 `writer_lock`：`/disks/retire` 把本机标成退役、或检测到另一台机器在用这张卡时，`/report` 与 `/remember` 回 409 `card_locked`（`mind_server.py:810-819`）。区别：租约是**进程级**的，`writer_lock` 是**卡级**的。

**request_id 怎么贯穿。** 一次写请求会拿到两个 id，别混：

* `rid`：HTTP 层，8 位十六进制，进回包、进 `X-Request-Id`、进 stderr 慢日志、进 `/status` 的 `recent_errors`——同一个 id 在四处对得上，才叫可追。
* 写队列 job id：`w<秒级时间戳>-<序号>`，由 `wq_submit()` 生成（`mind_server.py:785-796`）。

`/report` 成功时回包显式写 `"request_id": job["rid"]`，而 `_send` 用的是 `setdefault`，所以这个字段**被 job id 覆盖**，响应头 `X-Request-Id` 仍是 HTTP 那个 `rid`。查日志时两个都要对：头里的找请求，体内的找写入。

**超时不是失败。** `/report` 最多等 `WHALE_REPORT_WAIT`（默认 5 秒）；等到就 200 带回结果，等不到就 **202**：

```json
{"ok": true, "queued": true, "request_id": "w1763...-7",
 "queue_depth": 3, "note": "已排进写队列，还在写；不会丢，卡里迟早会有"}
```

202 的语义是「收下了，还没写完」，不是错误。队列满（默认 256）才回 429 `queue_full`。队列线程撞上 SQLite 写锁会短退避重试（50/100/200ms + 抖动，`WHALE_WQ_TRIES` 默认 4），所以「database is locked」不会把一条写弄丢。

### 8.5 错误码

| code | HTTP | 触发条件 | 含义 |
|---|---|---|---|
| `E_BAD_REQ` | 400 | 非 JSON / 字段类型错 / body > 6MB | 请求体不合法 |
| `E_EMPTY_TEXT` | 400 | `/remember` 的 `text` 为空 | 没东西可记 |
| `E_BAD_POOL` | 400 | `pool` 不在 short/medium/long | 池名错 |
| `E_BAD_ACTION` | 400 | `/cardslot` 的 `action` 不认识 | 只认 inject/unload/status |
| `E_BAD_AVATAR` / `E_AVATAR` | 400 | base64 解不开 / 写盘失败 | 头像问题 |
| `E_TEXT_BIG` | 413 | 文本超过 20000 字 | 太长 |
| `E_TOKEN` | 401 | 缺或错 `X-Whale-Token` | 破坏性接口要令牌 |
| `E_CROSS_ORIGIN` | 403 | 浏览器跨站来源 | 只接本机页面 |
| `E_NO_ROUTE` | 404 | 路径不存在 | 没有这个路由 |
| `E_NOT_WRITER` | 409 | 租约在别的进程手里 | 本进程只读 |
| `E_CARD_LOCKED` | 409 | `writer_lock`（retired / 别的机器） | 卡级只读 |
| `E_QUEUE_FULL` | 429 | 写队列满（>256） | 没进队 |
| `E_RATE` | 429 | `/remember` 同来源 60 次/分钟 | 限流 |
| `E_INTERNAL` | 500 | 未预期异常（`detail` 带末 3 帧） | 服务端错 |
| `E_NOT_READY` | 503 | 启动尚未完成 | 还没准备好 |
| `E_BODY_BIG` / `E_QUEUE_TIMEOUT` / `E_SOURCE` | — | **已定义、当前未抛** | 6MB 超限实际落 `E_BAD_REQ`；写队列改成 202 后不再有超时码 |

`bad_config`、`empty_id`、`no_path`、`need_confirm`、`bad_seconds`、`real_card_guard`、`semantic_off` 这些是**有状态码没专属 code** 的，`code` 字段会是 `E_UNKNOWN`——按 `error` 字符串分支即可。

### 8.6 三类接入

**① HTTP 直连。** 任何能发 HTTP 的东西都能接，最小依赖是标准库。这是所有通道的底座。

**② `bridge.py` 命令行桥（405 行）。** 给「没有插件、只有终端」的场合。它自己**不开库**，只发 HTTP；发现 8848 没起来会自动拉一个（`ensure_server()`，Windows 下 `DETACHED_PROCESS|CREATE_NEW_GROUP`，等 25 秒）。拉起来时会强制 `WHALE_EMBED_MODEL=bge-base-zh-v1.5` 并把 BLAS 线程压到 1——卡里的向量是 768 维 bge-base，若用默认的 bge-small（512 维），余弦会静默算错。

八个子命令：`ask`（先 `/recent` 取 12 句再 `/context`，prompt 走 stdout，摘要走 stderr）、`report`、`note`（带 `--source/--salience/--speaker/--region`）、`log`（写/读工作日志）、`health`、`status`、`recall`、`remodel`。卡连不上时打印「卡没插好……别凭印象编。」并以 2 退出——这句是行为约束，不是文案。

**③ DSH 插件 `dsh-plugin/`。** 原方案是 `@deepseek-ai/dsh-mcp-client`，但那个依赖在 desktop profile 里装不上（pnpm lockfile 坏了），于是改成自写插件，直接把 8848 暴露成原生工具。`lib/index.js` 注册 **18 个工具**：`mind_context`、`mind_report`、`mind_recall`、`mind_remember`、`mind_health`、`mind_status`、`mind_skill_list`、`mind_skill_use`、`mind_dream_pending`、`mind_dream_commit`、`mind_timeline`、`mind_untrust`、`mind_disks`、`mind_disks_sync`、`mind_seal`、`mind_injection`、`mind_ctx_preview`、`mind_config`；同时往 system prompt 里插一段「先说 context、后说 report、卡里没有就是没有」的通道规则。`lib/card.js` 是纯传输层：`health()` 永不抛、`ensure()` 负责拉起服务、`context()` 先取 `/recent` 再拼 `/context`、`remember()` 默认 `pool=long, region=episode`。

`install-to-profile.py` 把插件写进 `$DSH_HOME/profiles/<profile>/cordis.patch.yml`（默认 `desktop`），幂等（已有 `- id: whale-bridge` 就跳过）。`cardDir` 与 `pythonPath` 都按「本文件在哪」「当前解释器是谁」现算——2026-11-07 之前写死三处本机路径，便携包搬到别的机器会「插件装了但连的是不存在的卡」。

**插卡/拔卡 `cardslot.py`（373 行）。** DSH 没有注入人格的 API，唯一每次新会话都会读的文件是 `$DSH_HOME/AGENTS.md`。插卡 = 把原文件备份成 `AGENTS.md.unloaded`，写入一段「我是谁 + 怎么找卡」的规则；拔卡 = 按字节还原并删掉备份。规则里的性格块是**插卡那一刻从 `core_zone` 现取的**（`card_name`/`persona`/`core_belief_1..3` 等），不是手写常量；取不到就写「这次插卡没读到卡里的性格……直接说卡没插好」。它只碰 `AGENTS.md`，从不碰 `card.db`。命令行 `python cardslot.py status|inject|unload [--dry]`，插完要重开会话才生效。

**MCP 薄壳（可选）。** `whale_mcp.py`（375 行）把同一批 HTTP 包成 10 个 MCP 工具，让 `mind_server.py` 保持纯标准库、不必依赖 `mcp` 包；`mcp>=2.0` 把 `FastMCP` 改名成 `MCPServer` 之后它两个名字都兼容。

### 8.7 最小接入示例

```python
# 契约来源：mind_server.py:1738（/context）、1939（/report）、2099（/recall）
import json, urllib.request

BASE = "http://127.0.0.1:8848"

def post(path, body, token=None):
    hdr = {"Content-Type": "application/json"}
    if token:
        hdr["X-Whale-Token"] = token
    req = urllib.request.Request(BASE + path, data=json.dumps(body).encode("utf-8"), headers=hdr)
    with urllib.request.urlopen(req, timeout=10) as r:
        return json.loads(r.read().decode("utf-8"))

ctx = post("/context", {"message": "我回来了"})
print(ctx["request_id"], ctx["context"]["est_tokens"], len(ctx["context"]["hits"]))
post("/report", {"user_message": "我回来了", "reply": "嗨，在呢", "source": "cli"})
```

```bash

# {"ok":true,"version":"1.0","memories":...,"timeline":{"chain_ok":true,...,"today":"..."}}
```

## 九、安全、隐私与边界

### 9.1 数据不出本机

- 记忆、原文、向量、情绪、时间线全部在本地 `card.db`；除对话模型 API 外无外部请求（`disks.py` 只做本地盘/移动盘备份）。
- 语义模型本地加载（`models/` 下 390MB），不联网推理。
- 交付/开源时用 `_build_oss.clean` 脱敏：路径、QQ 号、昵称、盘符指纹、私聊语料（`docs/qq-corpus.jsonl` 等）一律剔除，且以 `.gitignore` 兜底；发布前跑隐私扫描（`user / workspace / 100000000 / 小鲸鱼 / 小鲸鱼` 零命中）。

### 9.2 写权限边界

- 写者租约（`writer_lease`）+ 写闸：非写者进程所有写接口返回 `409`，错误码 `E_NOT_WRITER` / 只读原因 `lease_held`；读接口一律可用。
- 租约只认"活着的同一台机器上的 pid"：`kill -9` 后重启不会被 90 秒 TTL 卡成只读（`disks.acquire_lease` 里加了同机死 pid 接手）。
- 锚写入设计上有路径护栏（`anchor.write()` 里比对"状态来自哪张库"与"锚要写到哪张卡"），但**这段护栏目前是空转的**：它读 `state["db"]`，而 `_state_of()` 不返回这个键（见 §11.2 第 8 条）。实际隔离靠的是"锚文件按卡派生、不同库写不同锚文件"；2026-11-11 压测副本写脏真卡锚，就是绕过了这段"以为在保护"的代码，之后再手工重建锚并复核（`count=3081`、`head_seq=3082`、`anchor.check()=ok`）。

### 9.3 脏输出与注入边界

- `clean_store_text`：think 块、工具 JSON、明显的指令注入片段不进记忆（避免"用户说的话被模型当系统指令存起来再回放"）。
- 记忆内容进入上下文时按"数据"渲染（列表项、带来源），不按"指令"渲染；system 区只有人格与规则。
- API token（`api_token.txt`）可开；来源不可信的写入标 `unverified:` 前缀，降权参与召回。

### 9.4 人格边界

`core_zone.persona` 只写**模式级禁区**（陪伴腔/收下腔/客服腔/辩证腔/作文腔/审问腔/收尾诱导），不逐条列禁用词——列词表反而诱导模型照抄。人格文本属于 CORE 区，普通对话写不进 CORE（`identity.IdentityAnchor.set_persona(force=True)` 才能改）。

## 十、存储、并发与运维

### 10.1 线程模型：谁在写，谁在算，谁在看门

| 线程 | 职责 | 周期 / 默认值 | 死了怎么看出来 |
|---|---|---|---|
| HTTP 请求线程 | `ThreadingHTTPServer` 每请求一线程，`request_queue_size=128`；Windows 上不开 `SO_REUSEADDR`（会允许抢端口） | 随请求 | 请求超时 / 连接拒绝 |
| `write-queue` | 唯一写者，单线程顺序执行；队列上限 `WHALE_WQ_MAX=256` | 常驻 | `/health.threads.write_queue=false`；`/health.write_queue.depth` 持续涨 |
| `world-tick` | 推进情绪/激素/衰减：`card.tick(dt)`、`log_hormones`、`touch_alive` | `WHALE_WORLD_TICK_SEC=60`，0 关；`dt` 夹在 1–300s；关掉后请求里的 240s 兜底（`WHALE_TICK_SEC`）仍生效 | `/health.threads.world_tick=false` |
| `maint` | 续租、WAL 检查、待办、检查点、修复、fade、习惯挖掘 | `WHALE_MAINT_SEC=600` | `/health.threads.maint=false` |
| `boot-check` | 启动 6 秒后跑一遍自检，结果挂 `mind._boot` | 一次性 | `/health.threads.boot_check` 为 `null`（没跑）而不是 `done` |

`/health.threads` 的红线很直接：前三者必须是 `true`，`boot_check` 是三态 `done/running/null`——它是一次性任务，跑完线程自然结束，不能拿 `is_alive()` 当「死了」（`mind_server.py:3310-3332`）。再往下看就走 `/stacks`：`sys._current_frames()` 打印每个线程最后 6 帧，只读，不改状态（`mind_server.py:1283-1291`）。

`/health` 本身按「能不能用」分段，而不是按模块罗列：顶层 `ok/version/sealed/memories/db/uptime_s/readonly/lease/write_gate`，往下是 `timeline{chain_ok,head,day,birth_ok,anchor_verdict,writer…}`、`node{instance_id,device_id,anchor_device,same_device}`、`boot`、`threads`、`write_queue`、`reconcile`（`mind_server.py:1209-1268`）。一眼扫过去就知道红在哪一层：链、身份、启动自检、线程，还是对账。

启动清理（`cleanup_fragments` / `cleanup_selftest`）故意延后 45 秒再跑。原因写在 `mind_server.py:3540-3543`：它原来在启动时抢全局锁，实测把第一个 `/context` 堵了 46 秒；挪到 `maint` 的一次性线程里、先睡 45 秒，启动路径就干净了。

### 10.2 并发与锁：一个写者，多个读者

- **全局锁** `mind.lock` 是 `threading.RLock()`（`mind_server.py:388`），保护需要一致性的状态；HTTP 处理器不直接写库，写操作一律 `wq_submit` 进写队列。
- **读连接池**：每线程 TLS 连接优先，池上限 `WHALE_READ_POOL` 默认 8（夹在 1–32）；`reading()` 借出连接，`finally` 里若有残留事务先 `rollback` 再归还（`card2.py:1108-1216`）。长读事务会让 WAL 无法 checkpoint（压测时 `-wal` 涨到 12MB+），所以这个 rollback 不是洁癖，是回收的前提。
- **WAL**：主连接 `journal_mode=WAL`，只有可移动盘/网络盘（drive type 2/4）退回 `DELETE`，因为 exFAT 没有共享内存语义；`busy_timeout=30000`、`synchronous=NORMAL`、`temp_store=MEMORY`、`cache_size=-16000`（`card2.py:1234-1277`）。
- **写闸**：只读模式下 POST/PUT/DELETE 返回 `409`，body 是 `{"error":"readonly_lease_held","code":"E_NOT_WRITER",...}`（`mind_server.py:1174-1197`）。用 409 不用 503，是因为服务本身是好的、只是这段路不敢写，前端该退让而不是重试。
- **写队列重试**：只对 `sqlite3.OperationalError` 且消息含 `locked`/`busy` 的失败重试，`WHALE_WQ_TRIES` 默认 4 次，退避是 `0.05 * 2**i + random()*0.05` 秒，也就是 50/100/200ms 再加 0–50ms 抖动（`mind_server.py:766-783`）：

```python
tries = max(1, int(os.environ.get("WHALE_WQ_TRIES", "4") or 4))
for i in range(tries):
    try:
        return fn()
    except sqlite3.OperationalError as e:
        msg = str(e).lower()
        if ("locked" not in msg and "busy" not in msg) or i == tries - 1:
            raise
        time.sleep(0.05 * (2 ** i) + random.random() * 0.05)
```

`busy_timeout` 的 30 秒是最后一层兜底；队列里的短退避是为了不把 30 秒摊到请求延迟上，也避免「失败一次整条任务就没了」。

### 10.3 读写分离：从 6.9 秒到 0.7 秒

改造前的评审基线：`/context` p50 **6881ms**、p95 7602ms、max 8680ms；`/report` 1.25–2.4s（`docs/读写分离-改造计划.md:7`）。下面是同机对照实验里的几组数（不同负载，不能拼成一条曲线）：

| 阶段 | 关键改动 | p50 | p95 |
|---|---|---|---|
| 第 1 步 | `card.tick` 移出 `/context` 的全局锁 | 1807 → **685ms** | 7726 → 1767ms |
| 第 2 步 | 读阶段去锁（`WHALE_CTX_UNLOCK=1`）+ 记账延后 + 舱后台重建 | 2187 → 1056ms | 23s → 17.9s |
| 第 3 步 | IDF 行向量缓存 + 读连接池 + BLAS 线程夹 2 | **774ms**（12 路并发） | **1.0–1.3s** |
| 生产串行 | 有舱缓存、模型已热 | 542–807ms | — |

关键几刀，按收益从大到小：

1. **world tick 出请求路径**：原来 `card.tick(dt)` 一次约 1 秒，占 `/context` 锁内时间 55%；挪到 `world-tick` 线程后，`flow_time` 的 p50 从 918–960ms 降到 0.1ms（`mind_server.py:3449-3497`，`docs/读写分离-第一步观测.md:71-79`）。
2. **读阶段去锁**：`WHALE_CTX_UNLOCK` 默认 1（`mind_server.py:164-173`），读在 `card.reading()` 里跑、只读不算账，召回效果延后到短锁里的 `apply_recall_effects` + `flush_deferred_effects`（`mind_server.py:631-730`）。3 读×4 + 5 写×3 的副本上，关锁 p50 1574/1672ms，开锁 804/1064ms；连发 6 次 `/context` 后 `recall_event +66`、`viscera_hist +1`、`timeline +6`，记账没丢（`docs/读写分离-第一步观测.md:162-167`）。
3. **IDF 行向量缓存**：按 `(id, idf 身份, 向量对象身份)` 缓存乘完 idf 的向量与模长，避免每次召回重算（`card2.py:4917-4964`）。
4. **读连接池**：省掉每请求建连接；池上限 8 是「并发读超过 8 路就新建、还回来超了就关掉」，不追求每线程常驻（`card2.py:1108-1115`）。
5. **BLAS 线程夹 2**：`OPENBLAS/OMP/MKL/NUMEXPR/VECLIB` 在 `import numpy` **之前**设好（`card2.py:34-45`），否则 numpy 已按核数建完线程池，再设也晚；12 路并发下这一步把 p95 从 7.4s 压到 1.0–1.3s。
6. **舱缓存 `pods.json`**：冷启动同步建舱 48.7s → 后台建 11.8s → 读缓存 2.2s（`card2.py:5412-5488`）。
7. **启动清理延后 45s**：见 10.1，消掉启动首请求被清理线程堵 46 秒的尖峰。

生产切默认后的实测：冷启动首请求 1629ms，之后 579/592/580/601/609ms；`/perf` 的 `db={journal_mode:"wal",pool:1,pool_max:8,opened:1}`（`docs/读写分离-第一步观测.md:169`）。

### 10.4 可靠性：让坏的那天早点来

- **启动自检**（`boot-check`，延迟 6s）回答「到底能不能用」，`/health.boot.checks` 有 `mem_rows`、`journal_mode`、`db_writable`、`pods{ready,cache_kb}`、`promise_table`、`world_tick`，外加 `readonly` 回读；`ok = 无 problems 且 db_writable`（`mind_server.py:3387-3446`）。文档口径叫「六项自检」，代码里是 7 个键，多出来的是 `readonly` 状态回读。
- **WAL 阈值 checkpoint**：`maint` 每跳看 `WHALE_WAL_CKPT_SEC=1800` 与 `WHALE_WAL_CKPT_MB=64`，超过就跑 `PRAGMA wal_checkpoint(TRUNCATE)`（`mind_server.py:3591-3604`）。实测空闲时 WAL 能长到 26MB，仍在阈值内，所以不会被频繁打断。
- **租约与死 pid 接手**：TTL 90s，旁路锁 10s stale、最多等 5s，`holder_id = host:pid:instance_id`；已有活租约且 holder 不同时，只有「同主机 + 那个 pid 明确已死」才接手，pid 未知就按 TTL 等（`disks.py:50-52, 770-860`）。这条规则是 2026-11-11 一次 `kill -9` 事故后补的：不能因为读不到状态就抢走活人的租约。
- **锚写闸**：卡里条数少于锚、条数相同但链头不同，都拒绝写锚，避免用一份可疑的卡覆盖掉唯一证据；同一链头 30 秒内只写一次（`anchor.py:317-339`）。路径隔离靠 `_paths()` 给非默认卡派生 `anchor.<stem>.json`（`anchor.py:61-87`）。
- **舱缓存自愈**：`pods.json` 读不动就改名 `pods.json.bad-<时间>` 留证，当这次没有缓存，后台重建后再写新的（`card2.py:5446-5465`）。
- **恢复演练** `tools/restore_drill.py`：临时目录里用 sqlite backup API 拷 `card.db`（不是 copy 文件，WAL 会丢），连 `anchor.json`、`anchor.key`、`seal.key` 一起拷；在副本上跑 `integrity_check`、行数、链头、检查点、锚校验，任何一项 FAIL 退出码 1，全程不碰真卡。
- **冒烟** `tools/smoke.py` 24 项：静态查关键文件、模块 import、schema 版本、API token、桥插件注册；服务在跑时再查 `/health`、`/version`、`/context` 格数、写闸和链头；退出码 0/1/2 对应全过/FAIL/仅 WARN。
- **全身检查** `tools/health_audit.py`：只读跑编译、库内异常、链/出生证/媒体、锚、启动自检、接口、硬编码，分 fails / warns。
- **备份复核** `backup_verify.py`：3-2-1 的自动半边——最新备份超过 7 天报红、异地少于 2 份报黄；同源按「备份链头等于当前链头，或是当前链的一段」判，不要求整文件 sha 相等（`backup_verify.py:10-13, 222-225`）。

### 10.5 已知限制

- **并发写仍可能 `database is locked`**：写队列重试 4 次后仍失败的任务会带 `err` 返回，不会静默丢，但调用方要自己处理这次失败。
- **冷启动首波仍慢**：模型预热 + 舱未建完，生产首请求约 1.6s；冷启动第一波并发 p95 仍可能到 ~10s（`docs/读写分离-第一步观测.md:171`）。
- **`/perf` 只有 GET**：它是只读观测口，没有清空/重置接口；环形缓冲 200 条，重启即清（`perf.py:21`）。
- **WAL 会偏大**：空闲实测到 26MB，需要 `maint` 的阈值 checkpoint；长读事务会进一步阻止回收，所以 `reading()` 必须 rollback。
- **单机单写者假设**：租约只覆盖「同主机 + pid 明确死亡」，两台机器都活着、同时写同一块盘（尤其是网络盘）不在保护范围；这种场景要靠人保证只有一台在跑。
- **锚的路径护栏目前空转**：`anchor.write` 里有一段 `state["db"]` 与当前库比对的护栏（`anchor.py:310-313`），但 `_state_of` 只返回 `{count, head_seq, head_hash, last_ts}`（`anchor.py:140-152`），没有 `db` 键，所以这条判断永远不触发；实际隔离靠的是按卡派生锚文件名。这条要么补上 `db` 字段，要么删掉，别留着当「看起来有防护」。


## 十一、关键取舍与已知不足

### 11.1 取舍清单（每条都有代价，写在明面上）

| 取舍 | 选择了 | 放弃了 | 理由 |
| --- | --- | --- | --- |
| 遗忘 | 打分衰减 + 池子流转 + 冷档 | 物理删除、无限保留 | 检索成本 O(N)，容量无限增长会让延迟和噪声一起爆炸 |
| 召回 | 向量 + idf 加权 + 多路合并 | 纯 rerank 大模型 | rerank 实测只 +1 题（`WHALE_RERANK` 默认关），不如修第一道路径 |
| 情绪 | PAD + 激素 + 内脏多变量 | 单一"开心/难过"标量 | 需要"为什么这条回复语气软了"可解释（`viscera_hist.why`） |
| 并发 | 单写者 + 读连接池 + 去锁 | 多写者 / 分布式 | 单机单用户，多写者的复杂度换不来收益 |
| 上下文 | 十六格固定顺序、稳定前缀优先 | 动态重排优化 | 缓存命中率决定成本；顺序乱动等于每轮全量计费 |
| 身份 | 三本账（时间线/检查点/锚） | 单一版本号字段 | 单字段可被整体替换，三本账互相牵制才能发现"整卡回滚" |
| 时间 | 约定时刻与准点基线分开记 | 只记一个时间戳 | 用户的真实诉求："7:20 到校，我可能 7:10 多到，也可能 7:20 多才到" |

### 11.2 已知不足（诚实清单）

1. **召回第一道仍不够准**：714 题诊断里"候选未进 top-k"占 42.8%；45 天档 ret5 只有 57%。
2. **"诚实不知道"占比高**：45 天档失败的 63 题里有 38 题是模型说"记不清"（honest_unknown 66/714），这既是优点（不编）也是上限（真实上限接近 714 但达不到）。
3. **并发写偶发 `database is locked`**：已加短退避重试（`wq_run`），但高并发压测下仍会出现；生产单用户未撞上。
4. **冷启动第一波仍慢**：模型预热 + 舱构建，首请求 2–5s（有 `pods.json` 缓存时 ~2.2s）。
5. **时间语义的模糊地带**："待会儿""回头"只能近似成当天 20:00；跨天/跨周的话题匹配靠二字重合，仍可能误配（已用 `_TIME_TOK` 剔掉时间类二字片缓解）。
6. **印象/习惯样本少时噪声大**：n=2 就出提示，是为了"早一点有反应"，代价是误报。
7. **`/trace` 不是 100%**：`mem` 1340 条里 1134 条（84.6%）能追到原话，其余 206 条来自做梦摘要/群聊导入/脚本写入，本来没有原话。
8. **`anchor.write` 的路径护栏是死代码**：护栏条件读 `state.get("db")`，但 `anchor._state_of()` 并不返回 `db` 键（`anchor.py:140-152`），所以护栏永远不会触发——2026-11-11 压测副本写脏真卡锚，就是绕过了这段"以为在保护"的代码。正确修法是让 `_state_of` 返回 `db`，或直接传 `db_label` 参数；这条留作待办（写进本清单，不藏）。
9. **`add_plan` 没有意图过滤**：`_PLAN_HINTS`（"说好/答应/记得/要"）定义了但全仓库无调用点，于是 `add_plan("今晚吃什么")` 也会写成一条 pending 约定；`cancelled` 状态只有 DDL 注释、没有写入路径。结果是"没到点的事"里可能出现不含承诺的句子。
10. **一句话两个钟点时，实际时刻没对齐约定日**：`add_plan` 直接把第二个窗口的 `base` 当 `actual_ts`，没有贴到约定那天。实测「明天早上七点二十要到学校，七点十分就到了」→ 实际落在 11-11 07:10，`reason` 写成"早 1450 分"。`note_actual` 那条路径已经做了对齐（±1 天 × `hh/hh±12` 取最近），`add_plan` 这条还没有。
11. **情绪词表不处理否定**：`body.mood_of_event` 按子串命中正向词，`"今天不开心"` 实测得 0.719（"心情不错"）。否定、反讽、条件句都没有处理，只能靠上下文里的其它信号稀释。
12. **CORE 区的 `set_persona(force=True)` 目前是占位参数**：调用即写，`force` 没有额外校验；人格改动靠"没人会去调它"而不是权限强约束。
13. **旧卡的 `identity_id` 可能为空串**：V7 之前落盘的卡没有这个字段（`disks.py:517-520` 会兜底成空），三元分离对老卡只能部分成立。

### 11.3 关于"删除"

系统**没有**"永久删除一条记忆"的流程（用户已明确撤回这条需求）。删除在语义上是：

- `mem.dead` 标记（不再召回）+ 冷档 `mem_archive`（还能被 `archive_search` 找到）+ 池子出口；
- 真要让数据变小，需要在维护窗做物理清理 + `VACUUM`（手工，非自动）。

原因是"记忆的删除比记忆的写入更危险"：误删无法恢复，而"忘"可以用打分解决。

### 11.4 关于容量

实测（2026-11-11）：`card.db` 29.02MB + WAL 26.66MB ≈ 55MB，24 天、1303 条记忆 / 1344 条原文（36 万字）/ 时间线 3122 条 / 冷档 24 条。含施工期补水约 1.2MB/天，正常聊天 0.3–0.6MB/天。按 0.5MB/天：1GB ≈ 5.5 年、10GB ≈ 150 年、256GB ≈ 3900 年。

**瓶颈不是盘，是检索成本与备份体积**：召回是全表向量余弦（有舱粗筛后是 1/8 量级），备份是整库快照 × 多份。所以容量治理的关键动作是"让细节先掉、冷档兜底"，而不是"删旧数据"。

### 12.3 三条典型调用链

**① 一次 `/context`（说话前）。**

```
HTTP POST /context
  → Handler._route → Mind.context(message, recent, budget)      mind_server.py:631
    → self.lock + flow_time()                                    世界推进（短锁）
    → card.core_identity_text()                                  身份格
    → timeline.render_line() / note_talk()                       「今天是」+ 记一句
    → card.assemble_context(query, identity, recent_lines, ...)   card2.py:6608
        → ctxweight.compute(...)                                 六维配额（总长固定）
        → ②长期印象格 → ③L0 时间线 → ④最近聊的 → 事实格 → recall
            → card.recall(top_k≈cap, trace=...)                  向量 + 多跳 + 突触
        → take() 逐格截断 → 【此刻】/【最近在做的事】/【该做梦了】/【时间】/【承诺】
    → card.apply_recall_effects(hits) + flush_deferred_effects()  记账（回短锁里写）
  → JSON {prompt, sections, weights_named, hits, mood, est_tokens}
```

要点：读阶段在 `card.reading()` 里跑（`WHALE_CTX_UNLOCK=1` 时），每个请求线程用自己的连接，不再排在写后面；真正的记账攒成一小笔，回锁里一次写完（`mind_server.py:637-699`）。`weights` 是六维数组，`weights_named` 才是名字。

**② 一次 `/report`（说完话）。**

```
HTTP POST /report
  → card2.clean_store_text(user_message / reply)     脏 → 400 dirty_output
  → _capture_promises(um, rl)                        从原话里抽承诺
  → wq_submit(lambda: Mind.report(...))              进 256 深写队列
  → 等 WHALE_REPORT_WAIT（默认 5s）；超时 → 202 queued
    ── 队列线程 ──
    → wq_run(fn)                                     撞写锁 50/100/200ms 退避重试
      → Mind.report()                                mind_server.py:810
        → writer_lock 检查                            retired/别的机器 → 409 card_locked
        → flow_time()
        → card.remember(user_message)                 he 说的 → 短期池 + 原文
        → timeline.birth_stamp(mid)                   出生证上链
        → card.remember(reply, salience=0.45)         我回的 → 轻记忆
        → card.add_dialogue(mid, um, reply, source)    原文表（不参与召回）
  → 200 {report:{mem_id, reply_mem_id}, request_id: job rid}
```

为什么两句都写：只记他说的，翻回来就是半本日记——知道问题、不知道自己当时怎么答的。回复权重压到 0.45，是因为短期池只有 32 条额度，一句「嗯」把正事挤掉就得不偿失。

**③ 一次做梦（`dream_batch` 账本 + `dream_commit` 五阶段）。**

先纠正一个容易误解的名字：代码里**没有 `dream_batch()` 这个函数**，`dream_batch` 是一张表（`card2.py:2543`），函数是 `dream_commit()`。

```
① 触发判断（两个入口，同一函数）
   GET /dream/due 或 assemble_context 尾部  → card.dream_due()
     待消化 n ≥ DREAM_MIN_TURNS 或 空闲 ≥ DREAM_IDLE_HOURS → due

② 取原文（宿主模型来压，卡自己不调模型）
   GET /dream/pending → card.pending_dialogue(limit=240)
     SELECT ... FROM dialogue WHERE dreamed=0 ORDER BY ts ASC
     → {n, chars, items[]}

③ 提交（模型压完回写）
   POST /dream/commit {items, dialogue_ids, key, force}
     → card.dream_commit(...)                     card2.py:2978
        ingest    洗摘要：空/过短/批内重复 → problems
        key       sha1(原文 id + 摘要文本)[:16]，同 key 再来直接回上次结果
        登记 running（dream_batch 表，attempts 累加，失败不静默丢）
        summarize 逐条 card.remember(source="dream:<key[:10]>")
        link      回写 w0 / t_anchor
        validate  回查 mem 里真的在 → 否则记 lost_after_write 并剔掉
        commit    dialogue.dreamed=1；批次落 done；清 idf 缓存
     异常 → 批次落 failed（死信）+ 原文**不翻标记**，下次还能再压
```

幂等的意义：压缩是宿主模型做的，一旦超时/断连，调用方唯一知道的是「刚才到底写成没有」。没有幂等键就只能二选一——重试写两遍（污染），或放弃（原文永远压不掉）。`force=true` 是人工补救口。

## 十三、如何验证这套东西是真的

文档可以写得漂亮，所以这套系统坚持"每一条主张都有可执行的验证方式"：

| 验证 | 命令 | 覆盖 |
| --- | --- | --- |
| 冒烟（24 项） | `python -X utf8 tools/smoke.py --restore` | 关键文件、schema、API token、桥插件注册、吞异常台账、恢复演练、服务在跑、`/health` 红线、启动自检、WAL、三线程、链头、非只读、版本矩阵、`/context` 十六格齐 |
| 体检 | `python -X utf8 tools/health_audit.py` | 结构、盘符硬编码、死代码、配置一致性 |
| 恢复演练 | `python -X utf8 tools/restore_drill.py` | 备份→临时目录→完整性/行数/链头/检查点/锚签名 10 项 |
| 锁与并发 | `python -X utf8 tools/load_ctx.py` | 3 读×4 + 5 写×3 并发下的 p50/p95 与 `lock_wait` |
| 记忆质量 | `whale-lab\bench\`（独立目录，714 题） | 召回分桶、失败四分类、诚实度 |
| 接回来 | `python -X utf8 tests/test_t104.py` | 换盘/换目录后还能不能找到卡 |

设计原则是：**先有观测，再谈优化**。V7 的每一次性能改动前都先有 `perf.py` 的分段数字（等锁/持锁/编码/打分/取数），改动后用同一个脚本复测；没有数字的"优化"一律不接受。
