# 读写分离：从「先不动」到分阶段改造（2026-11-11）

评审原文：`docs\_读写分离评审_原文.txt`（《读写分离专项 技术评审与改造建议》，用户 2026-11-11 13:16 下载）

## 评审结论（与我们的实测对得上）
- 根因不是 SQLite WAL，而是**应用层一把 `mind.lock` 把读写人为串行化**，且写路径把 embedding / consolidate / 原文落库 / 时间线 / 记账等耗时操作放进锁内。
- 基线：`/context` 中位 6881ms、p95 7602ms、最慢 8680ms；`/report` 1.25–2.4s。
- 推荐：方案三（锁内只做短事务、慢活丢后台）为目标；方案一（只读连接、读不拿锁）+ 方案四（批量短事务）为第一阶段；方案二（连接管理）打底。

## 我们的现状（V7-11 🟡）
- ✅ 写队列：`/report` 入单写队列返 request_id，单条 1.25–2.4s（原 4.3–28.9s），队列深度进 `/health`。
- ❌ `/context` 仍拿全局 `mind.lock`；请求级连接的 PRAGMA 初始化未统一；派生任务（embedding 等）仍在写路径内同步做。

## 分阶段计划
1. **可观测性**：拆出「锁等待 / 持锁 / SQL 事务 / embedding / consolidate」五段耗时，进慢日志与 `/health.latency`。不达这一步不动后面任何代码。
2. **读路径去锁**：`/context` 走独立只读连接（`file:…?mode=ro`）、不拿 `mind.lock`、一次短只读事务批量取数，事务外再排序拼装；响应带 `snapshot_revision`。
3. **连接管理**：启动设 `journal_mode=WAL` 并校验返回值；连接级 `busy_timeout`/`foreign_keys` 每连接配一次；固定单写连接 + 读连接池，禁止请求级重复 PRAGMA。
4. **写路径 Outbox**：核心写入与任务同事务提交；embedding/consolidate 由持久化任务表 Worker 执行（lease/retry/dead_letter/幂等键/processor_version/积压监控）。
5. **验收**：同一压测脚本对比（纯读、读写混合 5×3 写 + 3×4 读、突发、Worker 停机/崩溃、重复投递、SQLITE_BUSY、长读事务、磁盘满、备份恢复），看 p95/p99 与尾延迟，不看平均值。

## 纪律
- 每阶段单独上线、单独压测、可单步回退；改的是生产 8848，动锁前先备份 + 记 `docs\并发与锁-20261110.md`。
- 不动「删除语义」（用户已撤回）；不为了压测数据降低 `synchronous` 持久性。
