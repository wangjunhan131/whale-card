## 0. 一句话结论

**它这块「承诺/计划状态机」是我们真缺的，而且缺的是一条完整的链**：卡里现在能存「发生过什么」（mem / timeline / fact），也能存「最近 72 小时发生过什么」（`card2._l0_lines`），但没有任何东西记住**「说好了、还没做」**。缺的不是表，是三样东西的组合 ——
① 一个带**未来到期时刻**的账本；② 一个**到期判定**（谁在什么时候把 `open` 推成 `due`）；③ 一个**结算触发器**（把「该做没做」翻译成一次 RPE 负误差）。

SYNAPSE 那套把 ①②③ 串起来了，但它顺带绑了 18 个字段的事件表、同义词表、三个出戏检测 —— 那些不是我们缺的。**我们缺的是最中间那条竖线，不是那一整面墙。**

## 2. 状态集合

不是「四态」，是 **2 个活跃态 + 3 个终态**（`event_type='plan'` 才有状态机；`fact` 类型直接 `done`）：

```
pending ──(到点，expect_end < now)──▶ expired      ← 判失约，进情绪结算
   │
   ├──(匹配到完成)──▶ done                        ← 进情绪结算（正/零）
   └──(用户说算了/不弄了)──▶ cancelled             ← 进情绪结算（被推开）
```

- `sweep_expired()` 只扫 `event_type='plan' AND status='pending' AND expect_end < now`，**返回明细列表**（含 `id / topic_key / kind / importance / late_hours`），给上层去结算 —— 扫描只改状态，不自己算情绪。这个分工是对的。
- `match_completion(topic_key)`：靠 `topic_key` + `topic_alias` 同义词表匹配；**多条候选就拒绝自动关闭**，返回 `ambiguous`。宁可漏判，不乱关。
- 我们的五态 `open / due / kept / broken / cancelled` 是把它拆细了一档：**把「到点」和「失约」分开**。理由见 §6.1。

## 3. 字段（`events` 表）

```
id, content, raw_text, event_type, status, created_at,
expect_time, expect_end, mark_time, tz, subject, topic_key,
parent_id, superseded_by, source, reason, meta, kind, importance
```

真正支撑状态机的只有 7 个：`event_type / status / expect_time / expect_end / mark_time / topic_key / kind`。
其余是审计与展示（`raw_text` 留原话、`tz` 存时区、`parent_id/superseded_by` 处理「改口」、`meta` 放扩展）。

我们原型只留 `id, ts, who, what, due_ts, state, closed_ts, note` —— 因为**我们不需要「改口链」和时区**（单机单卡、只服务一个人），而 `what` 直接存原话就够追溯了。

## 4. 结算时机

| 时机 | 入口 | 权重档 |
|---|---|---|
| 约定成立 | `on_plan_created(topic, kind, importance)` | 抬 expect：`0.74 * (0.6+0.4*importance)` 写进 `eng.expect[...]`，与已有预期取 max，上限 +0.05 |
| 临期未到 | `on_plan_soon(...)` | 小负（`cap` 0.10） |
| 到期未做 | `on_plan_expired(late_hours)` | `neglect .30 / cold .08 / attention .30`（agreement），`cap` 0.30 |
| 兑现 | `on_plan_completed(late_hours, early_hours)` | `care .50 / share .30 / praise .20 / attention .80`，`cap` 0.20 |
| 取消 | `on_plan_cancelled(by_user)` | 「被推开」余味 |

统一走 `_settle(topic, kind, outcome, elapsed_hours)`，内部三道防线（§7）。

**关键顺序**（`process_user_message`）：`sweep_expired → parse_events → apply_events → build_context`。
先结算旧的，再抽新的，最后拼上下文 —— 所以这一轮上下文里出现的到期项，是**已经结算过**的那批，不会同一件事重复扣两次。

## 5. RPE 公式

$$
RPE = V_{actual} - V_{expected}
$$

- `V_actual` 由 `Appraisal` 经 `engine.value_of()` 算出（底线 0.50，加权项见附录 A）。
- `V_expected` 取**衰减后**的预期：

$$
V_{expected}(t) = \max\left(0.35,\; 0.74 \times 0.5^{\,t/72h}\right)
$$

  半衰期 72 小时，地板 0.35 —— 意思是「说好了」这件事会随时间自然变淡，但不会淡到没发生过。

- 实测（总文档）：逾期 10h → V实 0.38 / V期 0.67 / **RPE −0.14**；兑现 → V实 0.71 / V期 0.67 / **RPE +0.19**。
- 本轮旁路原型实测（`probe/_promise_proto.py`，真卡副本，逾期 15h）：
  - 失约：**V实 0.384 / V期 0.640 / RPE −0.256**，DA −0.256、CORT +0.302、5HT +0.135
  - 兑现：**V实 0.826 / V期 0.740 / RPE +0.086**
  数值方向和总文档一致，量级略大（预期衰减到 0.640 而不是 0.67，因为逾期更久）。

## 6. 跟我们卡里已有的东西，哪些重合

| 旁路表先例 | `recall_trace`（`card2.py:2373`，`WHALE_RECALL_TRACE=0` 关，不进 mem 池、不参与衰减） | — | **可直接照抄的模式**：承诺表就该长这样，独立表、独立开关、不进召回 |
| 到期扫描 | 无 | `sweep_expired()` | **缺** |

| RPE 引擎 | `synapse_emotion`：`expected_for()` / `pending` / `Appraisal` / 五调质动力学，能算 RPE | 同一个引擎（vendor 里是拷贝） | **重合，且我们这版更干净**。但我们没有任何东西去**设一个「约定」预期** —— 引擎有 `expect` 字典，却没人往里写 `plan:...` |
| 情绪权重 | `estimate_appraisal(text, ...)` 规则打分，有 `neglect / attention / care` | `plan_bridge.KINDS` 按 outcome 给权重 | **缺**：我们只有「这句话让我感觉如何」，没有「这件事没做成让我感觉如何」 |

### 6.1 真正缺的三点（精确到「哪儿缺」）

1. **未来维度**：`cardtime.parse_event_time()` 解析的是事件**落点**（过去/当天的 12:00），`query_time_span()` 也只会往回看 3/14 天。我们**没有任何函数产出「一个将来的到期时刻」**。
2. **存续期与到期判定**：`timeline` 一旦写入就终态（只追加、不可改）。承诺必须是**可变状态**（open→due→kept/broken），且要能被一个「每轮开头跑一次」的扫描推动 —— 这个扫描现在不存在。
3. **结算触发器**：`synapse_emotion` 的 `expected_for(scenario)` 查 `expect_global`（0.52）—— 因为**没人写 `expect["plan:..."]`**。所以即便「他昨天说好今晚一起弄、今晚没来」，引擎也只会算出 `V实 0.5 - 0.52 = -0.02` 的环境噪声，而不是 −0.25 的失约落差。**落差不是引擎算不出来，是没人告诉引擎「你本来在等这件事」。**

换句话说：**缺口不在「记」，在「等」。** 卡里所有机制都在描述已经发生的世界；「等一个人」这件事没有地方存，也就没有落差可算。

### 6.2 不值得搬的部分

- `events` 的 18 字段 / `parent_id` + `superseded_by` 改口链：单机、单用户，改口直接 `close_promise(cancelled)` 再开一笔就够。
- `topic_alias` 同义词表：我们卡里有向量召回和规则抽取，靠 `topic_key` 精确匹配的收益不如维护成本。
- `post_check()` 三个出戏检测（过期还说明天 / 人在学校还催 / 计划当事实）：**想法值得偷**，但它是「措辞层」的活，应该在 `prompt`/`render_behavior_block` 那边做，不该塞进账本。
- `state_snapshot` 表：我们 `assemble_context` 每轮现拼，没有跨轮状态机缓存的需求。

## 7. 照抄时踩到的两个坑（写原型才发现的）

### 7.1 vendor 的 `v_expect` 报的和用的不是一个数

`plan_bridge._settle()` 把**衰减后**的 `v_expect` 传进 `_run_with_cap(ap, v_expect, cap)`，但 `_run_with_cap` 只是把它填进 `SettleResult.v_expect` 用于报告；引擎 `step()` 内部查的是 `expected_for(ap.scenario)`。

而预期被写在 `scenario_key(kind, topic)` = `"plan:agreement:卷子"` 下，`Appraisal.scenario` 却是 `"plan_expired"` —— **键对不上**，引擎查不到，静默退回 `expect_global = 0.52`。于是：

- 报出来的 `V期` 是 0.640，
- 真正参与 RPE 的是 0.52，
- 算出来的 RPE 是 `0.384 - 0.52 = -0.136`，跟报的 −0.256 不是一个数。

**我们的原型绕开了**：直接在 `eng.expect[ap.scenario]` 写预期（`probe/_promise_proto.py` 的 `settle()`，注释里写明了原因）。接生产时必须这样写，否则失约的落差会被砍掉一半。

### 7.2 「封顶」单次缩放不收敛

`value_of()` 有 **0.50 的地板偏移**（`0.50 + 0.30*praise + ...`），所以把 `Appraisal` 整体乘 `ratio` 只能把 `V_actual` 往 0.50 推，推不到 0。当预期 0.74、cap 0.30 时：

- 第一次：RPE −0.356（超 cap）
- 单次缩放 `ratio = 0.30/0.356 = 0.843` → V实 0.402 → **RPE −0.338，仍超 cap**
- 迭代到第 2 次才落进 −0.30 以内

实测就在原型输出里（`失约（预期不衰减）` 那一行：缩 1 次后仍 −0.338 > 0.300）。**结论：接生产时封顶要循环重算，不能只缩一次。** 原型用 `iterate=True` 最多 4 轮，收敛为止。

### 7.3 本地 `engine.step()` 没有 `learn=False`

vendor 的 `_settle` 调 `eng.step(ap, dt=1.0, learn=False)`，我们本地版签名是 `step(self, ap, dt=1.0)` —— 直接调会 `TypeError`。而且本地 `step()` 末尾**无条件**做 TD 学习 + 基线漂移。原型的等价做法：**每次结算新建一个引擎（`autosave=False`）**，单次结算 = 不吃历史、不落盘，等于「不学习」。接生产时若要复用长生命周期的引擎，得先给 `step()` 加 `learn` 参数（那是改主线，本轮不做）。
